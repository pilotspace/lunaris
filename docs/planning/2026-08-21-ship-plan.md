## The thesis

Lunaris does not need more engine. Four audits agree the retrieval core is
strong and the defects sit **at every boundary where the project meets a
stranger**. The competitive read reinforces it: TencentDB-Agent-Memory has
23.4k stars behind 173 files, 9 test files, one CI workflow and **zero
benchmark harness** — they have the story, we have the substance. The work is
to open the front door, stop the public surfaces reporting success falsely, and
make our numbers reproducible when theirs are not.

## The blocking fact

Lunaris 0.7.0 hard-rejects any Moon below `0.8.5` at connect
(`crates/lunaris-storage-moon/src/version.rs`). **Moon v0.8.5 is a published
release with zero binary assets** — verified `v0.8.5 assets=0` against
`v0.8.4 assets=48` / `v0.8.3 assets=48`; all platform tarballs 404; ghcr
returns `401` to an anonymous pull against a `200` control. The v0.8.4 binaries
that exist are refused by the handshake.

The only working Moon 0.8.5 is the source build at `~/.lunaris/bin/moon` on the
owner's laptop. This is an **undocumented internal-only dependency**, not a
broken release. Until W0.1 ships, every other task improves a product nobody
can start.

      Found by W4.8. It drives both SDKs through `EmbedderConfig.fastembed()`, an API **retired** by the v0.6

- [x] **F43** **The activation prior was inert in production** — **M** — NEW
  2026-08-26, P1, **FIXED same day** (`f32b898` RED / GREEN this branch).
  Found while scoping W1.8: before deciding whether the other recall surfaces
  should get the activation prior, I measured what the prior actually does.

  `boost_prior` was `min(BOOST_CAP, BOOST_K * ln(1 + max(activation, 0)))`.
  The `max(activation, 0)` is the defect. In ACT-R base-level activation is
  normally NEGATIVE — the retrieval threshold is negative too — so clamping
  negatives to zero collapses the whole operating range onto one value.
  `activation` is `ln(weighted * elapsed^-decay)` with `elapsed` in SECONDS,
  so it turns negative the moment `elapsed > weighted^2` (default decay 0.5):
  a cliff at 9s for one strong reference, 15 minutes for ten.

  Measured with the real functions, BEFORE writing a test:

      refs(weighted)  |    10s     1min   10min      1h      6h      1d      7d
      1 weak      (1) | 0.0000  0.0000  0.0000  0.0000  0.0000  0.0000  0.0000
      1 strong    (3) | 0.0000  0.0000  0.0000  0.0000  0.0000  0.0000  0.0000
      3 strong    (9) | 0.0716  0.0140  0.0000  0.0000  0.0000  0.0000  0.0000
      10 strong  (30) | 0.1179  0.0856  0.0185  0.0000  0.0000  0.0000  0.0000
      50 strong (150) | 0.1581  0.1377  0.1034  0.0650  0.0020  0.0000  0.0000
      500 strong(1500)| 0.1969  0.1835  0.1632  0.1440  0.1201  0.0967  0.0505

  `BOOST_CAP` (0.30) needs a weighted sum of 1.944e8 — 6.5e7 strong references
  — so it was never approached. Meanwhile `LedgerBoostProvider` pays up to k
  point `read_as_of` calls on EVERY service recall to compute it.

- [x] **F30** **`TimelineReconstruction` recall ignores the `source_prefix` it
  was constructed with** — **M** — NEW 2026-08-23. Found by investigating a RED
  board on `main`.

  `conformance-bindings` has been failing on `main` since 2026-08-22 07:23Z (4
  consecutive runs; last green `4860643c` at 07:06Z). The failure is
  `documentary_parity.spec.mts > timeline_reconstruction_parity_between_10_and_15`:
  `expected 12 to be 6`.

  `TimelineReconstruction::new(lunaris, scope, source_prefix)` hands the prefix
  to a `DocumentCorpus` and stores it as `self.corpus`. `ingest` forwards to
  that corpus, so writes ARE prefixed. But `between` and `as_of` never touch
  `self.corpus` — they build `TemporalQuery::<Documents>::new(self.lunaris)`,
  which takes neither a prefix nor a scope. So the read path returns every
  timeline event in the store within the window, whatever its source.

  The sibling recipe shows this is not the intended contract:
  `DocumentCorpus::search` post-filters `h.source.starts_with(&prefix)` after
  hydrate, with a comment explaining why the filter is post-hydrate rather than
  a `StoragePort` filter. `TimelineReconstruction`'s temporal reads skip that
  step entirely.

  **Why it surfaced now, and only in TypeScript.** The `per-driver parity
  (moon)` job runs three suites in sequence against ONE Moon with no flush
  between them. Python ingests the same 30-event fixture under
  `timeline:doc-11-03-py/moon/`, then TypeScript ingests it under
  `timeline:doc-11-03-ts/moon/`. Python runs first and sees only its own 6;
  TypeScript runs second and — because the prefix is not applied on read — sees
  both sets, 6 + 6 = 12. Before `238db43` ("make the bi-temporal VALID axis
  real") the graph-OFF ingest path wrote no `valid_time_ms` at all, so the
  `.between` window did not select the other language's rows and the bug stayed
  invisible.

  **This is a product defect, not a test-isolation defect.** Two timelines in
  one scope is the ordinary case the `source_prefix` parameter exists to serve;
  a caller gets the other timeline's events back. Fixing the test (unique
  prefixes, or a flush between steps) would hide it. The fix is to apply the
  corpus's prefix on the temporal read path, mirroring `DocumentCorpus::search`.

  A second, independent defect in the same suite: the run is not idempotent.
  Two runs against one Moon return 12 for the same reason plus re-ingest.
  Same family as **F28** — a suite whose result depends on what ran before it.

  **Fixed 2026-08-23.** `between` and `as_of` now post-filter on the prefix the
  recipe was constructed with, via a private `scoped` helper (so the RCPDOC-04
  ≤6 public-fn cap is untouched). Post-hydrate, mirroring
  `DocumentCorpus::search`, for the reason documented there.

  Three tests in `crates/lunaris-recipes/tests/timeline_prefix_scoped_recall.rs`,
  driven by a stub `StoragePort` — no live Moon, so they run in the ordinary
  workspace suite. The stub is deliberately permissive on `source` (a real
  backend cannot filter it either) and honours only `Filter::ValidTimeRange`.

  reds two of the three, and the third is the vacuity floor, which correctly
  stays green because it does not depend on the fix.

  **Known limitation, documented at the call site.** Post-filtering shrinks the
  result set and `TemporalQuery` exposes no `top_k` to over-fetch against, so a
  window crowded with other timelines can return fewer than the backend's
  default `k`. The third test pins the CI-scale case (two 30-event timelines,
  six of each in-window). Returning fewer of your own events is smaller and
  more visible than returning someone else's as if they were yours.

## ADD review sweep — findings (2026-08-21)

Reviewing PR #150 for case coverage rather than for correctness of the diff.
Both findings are the same defect class the branch keeps re-encountering: **a
check that reports nothing is indistinguishable from a check that passes.**

### S6 — conformance runners could skip themselves green (FIXED)

Every live-backend runner short-circuits to `Ok(())` when its backend is
unreachable. Correct on a laptop; wrong in `integration.yml`, where the Moon is
up and port-checked and the server is built before any test runs. There a skip
means the job stopped testing and reported success.

The stakes are concrete: the `/v1/forget` P0 is guarded by exactly one
assertion, `two_step_hard_delete`, which runs only inside
`run_protocol_lunaris_server.rs` — a file with **three** skip-to-green paths.
Six decision points total (including `src/bindings/mod.rs`, shared with the Py
and TS drivers) now route through `skip::skip_or_fail`; `integration.yml` sets
`LUNARIS_CONFORMANCE_STRICT=1`; `tests/no_silent_skip.rs` holds both halves.

Verified: strict proven both directions; guard mutation-verified on the SECOND
roster entry; full protocol suite runs 4.11s of real work under strict against a
live Moon.

### S7 — `probe_backend` tried only the first resolved address (FIXED)

`to_socket_addrs().next()`. On macOS `localhost` resolves `::1` first, so an
IPv4-bound Moon read as unreachable and the whole suite skipped green. All four
copies now try every address. Strict mode is what surfaced it — the skip had
been silent. Discriminated: `moon://localhost:6392` skipped before, runs after.

### S8 — `a_maintenance_compact` env race (FIXED, was the red board)

The one failing check on PR #150. `§2` set `LUNARIS_MOON_COMPACT_MIN` process-
wide while `§1` read it indirectly through the function under test. Gate now
passed as an argument. Mechanism proven deterministically, not by inspection.

### S9 — no post-forget absence assertion (FIXED)

`two_step_hard_delete` asserted the receipt (`rows_deleted == 1`) against a
genuinely seeded episode, which DOES discriminate the P0 — under the bug the
scoped scan matches nothing and reports 0. But every assertion read the
handler's own report of what it did, so a handler that reports a delete it never
performed passed. Step 4 now re-targets the deleted id and requires 404, the
contract `unknown_id_returns_404` already pins. Mutation-verified against a live
row.

### S10 — 12 of 15 python guards ran in no workflow (FIXED)

`scripts/tests/` holds 15 stdlib guards; workflows named three. The other
twelve — 66 passing assertions covering the hook adapters, capture signal gate,
contextd lifecycle and scope forwarding, turnkey verification, the Moon identity
probe and the session digest — executed nowhere. Not failing quietly; not
running. All 15 pass under `env -i` with an empty HOME, so wiring cost nothing.

ci.yml now discovers them by glob rather than listing three by name (a
hardcoded list is how the gap opened), and `test_gated_tests_have_a_runner.py`
— which existed to catch exactly this shape and did not police its own
directory — now asserts every guard has a runner, with a vacuity floor.

Two first-draft errors worth keeping: the RED passed because a *comment* in
ts-prebuild.yml ("No workflow ran scripts/tests/*.py before 0.6.1") satisfied a
presence check; and the first mutation was invalid because `unittest.main()`
exits before an appended `raise` runs, which nearly read as "the loop cannot
detect failures".

### S11 — nothing checked that npm entry points get published (FIXED)

`files` is an allowlist; anything absent is silently omitted from the tarball.
A package can declare `"require": "./lunaris.cjs"`, pass every test, publish,
and then throw MODULE_NOT_FOUND on first `require()`. Nothing packs a tarball
and inspects it, so `files` was the only thing standing in the way — and the
v0.6 rewrite had just added two new entry filenames by hand. Now ratcheted in
`test_npm_version_parity.py`, mutation-verified both ways (drop a file from
`files`; point an export at a nonexistent path).
