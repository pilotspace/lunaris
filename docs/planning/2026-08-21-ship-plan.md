## The thesis

Lunaris does not need more engine. Four audits agree the retrieval core is
strong and the defects sit **at every boundary where the project meets a
stranger**. The competitive read reinforces it: TencentDB-Agent-Memory has
23.4k stars behind 173 files, 9 test files, one CI workflow and **zero
benchmark harness** — they have the story, we have the substance. The work is
to open the front door, stop the public surfaces reporting success falsely, and
make our numbers reproducible when theirs are not.

## The blocking fact

Lunaris 0.7.0 hard-rejects any Moon below `0.8.5` at connect
(`crates/lunaris-storage-moon/src/version.rs`). **Moon v0.8.5 is a published
release with zero binary assets** — verified `v0.8.5 assets=0` against
`v0.8.4 assets=48` / `v0.8.3 assets=48`; all platform tarballs 404; ghcr
returns `401` to an anonymous pull against a `200` control. The v0.8.4 binaries
that exist are refused by the handshake.

The only working Moon 0.8.5 is the source build at `~/.lunaris/bin/moon` on the
owner's laptop. This is an **undocumented internal-only dependency**, not a
broken release. Until W0.1 ships, every other task improves a product nobody
can start.

- [x] **W1.4** Extend `forget` to chunk rows — **M** — CHUNK HALF DONE 2026-08-22; fact half split out (see below)
      **Traced 2026-08-22 — the defect is sharper than this line, and the fact half is a different task.**
      1. **The `bt` half is already done.** `hydrate.rs:57` gates on `bt.sys.1.is_some()`, and the
         soft-forget path stamps it. Nothing to write.
      2. **A HARD forget leaves the content recallable — this is the real bug.** `scan_matches_scoped`
         walks one prefix, `lunaris:{scope}:episode:`, so chunk rows are never matched. Recall stays
         clean under a SOFT forget only because `hydrate`'s third pass drops chunks whose parent episode
         is sys-closed:
         `.filter(|(_, chunk)| !matches!(episode_sources.get(&chunk.episode_id), Some((_, true))))`
         A hard forget `KvDelete`s the episode row, so that lookup returns **`None`**, and
         `!matches!(None, Some((_, true)))` is `true` — the chunk is kept and hydrates with an empty
         `source`. **The irreversible, D-21 confirmation-token-gated path is the leaky one**; the
         reversible default works. Two locally reasonable decisions compose into it, and each documents
         itself honestly ("forget v0 stamps only the `episode:` row" / "Missing episodes stay tolerated").
         Fix: `scan_matches_scoped` must also collect the matched episodes' chunk rows. Costs one prefix
         scan over the scope's chunks per call — including on the `ForgetTarget::Id` fast path, since no
         reverse episode→chunk index exists (ingest writes doctree/episode/chunk/vector and no back-link).
      3. **The fact half is NOT implementable as written** — it needs a schema change, not a wider scan:
         - `lunaris_extract::Fact` carries **no episode or chunk provenance**. `RawExtraction` has
           `source_chunk_id`, and it is dropped when the validated `Fact` is persisted
           (`crates/lunaris/src/ingest.rs:709`).
         - The fact key is `FactId::from_triple(subject, predicate, object)` — **content-derived**, so two
           episodes asserting the same fact write the SAME row. Deleting it on one episode's forget would
           erase another episode's assertion.
         Same shape for entities and relations (`EntityId = blake3(name || type)`) and communities.
         Doing this properly means per-fact contributing-episode provenance plus reference-counted
         deletion. Split it out; it is not an M.
      4. **`classify_indices` overclaims.** Every target reports `Kv + Vector + Graph` affected, but a
         forget only ever writes KV rows. The vector embedding and BM25 text stay in Moon's FT index
         after a hard delete — recall is clean (hydrate drops a hit whose chunk row is gone), but the
         bytes are still there, which is not what "hard delete" promises.
      5. Not carried in the chunk fix: the `doctree:` row (keyed BY episode id, so trivially addressable)
         has no `bt` field, and `build_soft_delete_op` silently writes the payload back unpatched when
         `bt.sys` is absent — a stamp that does not stamp. Including it needs that helper to fail loudly
         first.
      **DONE (chunk half).** `scan_matches_scoped` now sweeps the matched episodes' chunk rows, so a soft
      forget stamps them and a hard forget deletes them — neither depends on the episode row surviving.
      Full RED/GREEN against a live Moon, with the fix stashed for the red so it could not compile itself in:
      RED — `hard_forget_leaves_no_recallable_text_moon` FAILED ("the verbatim text survived a confirmed
      hard delete"), `hard_forget_removes_the_content_from_recall_moon` FAILED (`rows_deleted=1` with the
      hit still present and `source: ""`, the blank-provenance fingerprint of the missing episode row),
      5 pre-existing forget tests green throughout. GREEN — 7 passed / 0 failed.
      **Contract change, in CHANGELOG:** `rows_written`/`rows_deleted` now count ROWS, not episodes, so
      `forget(Id)` on a one-chunk episode reports 2. Four assertions moved to the discriminating `> 1`
      form (the one that fails if the chunk sweep is removed) rather than a brittle exact count; the
      conformance `rows_deleted == 1` became `>= 1`, keeping the zero-guard the P0 needs.
      **`matched` and the MCP `removed` stayed EPISODES — and getting that wrong is what CI caught.**
      The first draft let the row count leak through both, because `matched` was `matches.len()` and
      `removed` was `rows_written + rows_deleted`: two numbers that happened to equal the episode
      count right up until chunks were swept. Three `lunaris-memory-service` unit tests and the
      protocol suite's `id_target` went red on the PR. They were right to. An agent asked to confirm
      a deletion reasons in episodes — "about to delete 2 things" is a worse answer than "1 episode",
      and both DTOs document episodes. `matched` is now counted by episode-key prefix (NOT by parsing
      payloads for an `id`, which a `Chunk` also carries), and `removed` is `matched` on a committing
      call, 0 on a preview, read from the engine's own `preview` flag so the two cannot disagree.
      Two surfaces, two units, each named for what it counts.
      **Split out, NOT done:** (a) facts/entities/relations/communities — blocked on the content-hash
      keying + missing provenance described above; (b) the FT-index residue and the `classify_indices`
      overclaim; (c) the `doctree:` row.

## Decisions — settled 2026-08-21 (owner)

**Ship target: public OSS launch.** The Tencent framing. W0 (open the front
door), W2 (truth) and W3 (reproducible numbers) drive the order; the Helios
canary follows rather than leads. W1's two P0s remain a hard prerequisite
regardless — you cannot invite strangers to a `/v1/forget` that silently
no-ops.

**W3.2 — publish TWO NAMED OPERATING POINTS, not one.** A *fast path*
(rerank OFF, p50 ~20 ms, the shipped default) and a *quality path* (rerank ON,
~1301 ms p50). Both are real, both are measured, and naming them turns the
config split from a gotcha a competitor exploits into a tradeoff the buyer
chooses. Nothing already measured gets thrown away. Every table, doc and
benchmark row must now state WHICH operating point it describes — an unlabelled
number is the defect this decision exists to kill.

**W3.5 + W3.6 — lift headline, absolutes below.** Lead with lift on a fixed
agent harness and with token reduction, because that is ground we win and the
harness ships (Tencent's does not). Keep absolute LongMemEval / PersonaMem
scores as a secondary table for readers comparing against published Zep and
Mem0 figures. Both tables, in that order.

**W4.5 — gate the RAPTOR write behind a default-off flag.** Stops the LLM and
storage cost on every ingest immediately, keeps every line of code, and is
reversible the day a reader exists. Not deleted, not wired.

## The recall ratchet never gated the `quality` arm (2026-08-22)

Found while clearing W1.7. `perf-gates` was fine; `recall-ratchet` was not.

The two-arm N=40 ratchet (`5e37105`) has run **exactly once** — on the W4.16
merge push, run `32484079897`, commit `dc11319`. All four `quality` shards died
mid-question at the 70-minute ceiling, both fan-in jobs were `skipped`, and the
run concluded **`cancelled`** — which is not a red board.

This is the third road to the failure mode `eval_workflow_guard.rs` already
guards twice. STARTUP-01 was the first, the merge-train concurrency cancel
(`0662cf3`) the second, a job timeout the third — GitHub reports it with the
same word. The file's own comment had already named the shape: *"a cancelled
gate is indistinguishable from a passing one on a board with no required
checks."*

Measured from the run's own step timings and artifacts:

| arm | setup+build | measure | per question | outcome |
|---|---|---|---|---|
| `fast` | 7m07s | 46m02s / 10 q | 4.60 min | success, 53m total |
| `quality` | 8m02s | cut at 62m10s | ~12.4 min | **CANCELLED at 70m** |

All four `quality` shards completed exactly 5 of 10 questions and died inside
the 6th — not a flake, a structural impossibility. The 70 was derived for the
N=16 single-arm shape and survived `5e37105` untouched when N went to 40 **and**
a 2.7x-costlier second arm was added; the workflow comment still described the
old shape, so nothing in review contradicted it.

Two defects, both fixed in `c4a0726`:

1. **The budget.** `timeout-minutes` 70 -> 170, and now DERIVED —
   `the_shard_timeout_covers_the_work_the_matrix_asks_for` recomputes it from
   `offsets40.tsv` and the matrix. Change the manifest or the shard geometry
   and the guard catches the drift, not review.
2. **One arm's timeout voided the other arm's verdict.** `needs: measure` waits
   on the entire matrix, so four complete, green `fast` shards sat in artifact
   storage uncompared. `if: ${{ !cancelled() }}` on the fan-in lets each arm's
   own "expected 4 shard config files" assertion decide — that assertion was
   already correct, it simply never ran.

Both halves proven against the real artifacts from the cancelled run:

```
fast     RATCHET OK: any-gold 39/40 vs baseline 39/40 (tolerance 1, floor 38)
quality  exit 5 — FATAL: run is NOT FINAL (artifacts=24/40, ERR=4:
         [251, 266, 283, 289]) — a partial run can neither be gated nor blessed
```

So the `fast` arm was green all along and CI discarded the verdict. Worth
recording separately: that 39/40 baseline was blessed on **Darwin-arm64** and
reproduced **exactly** on ubuntu x86, same single miss (`134`) — a stronger
cross-platform result than the tolerance was designed to assume.

**MEASURED 2026-08-22 — run `32506983470`, all 10 jobs green.** The `quality`
arm produced its first verdict in the project's history, and the 170-minute
budget is what made it possible: the quality shards ran **116-120 minutes**,
comfortably past the old 70-minute timeout that had been cancelling them and
comfortably inside the new one. The fast shards ran 51-63 minutes.

| arm | J (any-gold, N=40) | wrong |
|---|---:|---|
| `fast` (rerank OFF, shipped default) | **97.5%** | `134` |
| `quality` (rerank ON) | **100.0%** | — |

Zero errored questions on either arm. The single `fast` miss is `134`, and
`quality` answers exactly that one correctly — so the cross-encoder pass buys
one question out of forty, cleanly attributable rather than lost in noise.
That is the evidence the two published operating points needed: `fast` is not
a degraded mode, and `quality` is not a rounding error. Both baselines are now
blessed from a real verdict rather than from a local run.

Note the `fast` result reproduces the Darwin-arm64 baseline **exactly**,
including which question misses — a third consecutive cross-platform match.

- [x] **F1** `ScopedLunaris::recall` bootstrap gap — `test_cross_scope_isolation`

## ADD review sweep — findings (2026-08-21)

Reviewing PR #150 for case coverage rather than for correctness of the diff.
Both findings are the same defect class the branch keeps re-encountering: **a
check that reports nothing is indistinguishable from a check that passes.**

### S6 — conformance runners could skip themselves green (FIXED)

Every live-backend runner short-circuits to `Ok(())` when its backend is
unreachable. Correct on a laptop; wrong in `integration.yml`, where the Moon is
up and port-checked and the server is built before any test runs. There a skip
means the job stopped testing and reported success.

The stakes are concrete: the `/v1/forget` P0 is guarded by exactly one
assertion, `two_step_hard_delete`, which runs only inside
`run_protocol_lunaris_server.rs` — a file with **three** skip-to-green paths.
Six decision points total (including `src/bindings/mod.rs`, shared with the Py
and TS drivers) now route through `skip::skip_or_fail`; `integration.yml` sets
`LUNARIS_CONFORMANCE_STRICT=1`; `tests/no_silent_skip.rs` holds both halves.

Verified: strict proven both directions; guard mutation-verified on the SECOND
roster entry; full protocol suite runs 4.11s of real work under strict against a
live Moon.

### S7 — `probe_backend` tried only the first resolved address (FIXED)

`to_socket_addrs().next()`. On macOS `localhost` resolves `::1` first, so an
IPv4-bound Moon read as unreachable and the whole suite skipped green. All four
copies now try every address. Strict mode is what surfaced it — the skip had
been silent. Discriminated: `moon://localhost:6392` skipped before, runs after.

### S8 — `a_maintenance_compact` env race (FIXED, was the red board)

The one failing check on PR #150. `§2` set `LUNARIS_MOON_COMPACT_MIN` process-
wide while `§1` read it indirectly through the function under test. Gate now
passed as an argument. Mechanism proven deterministically, not by inspection.

### S9 — no post-forget absence assertion (FIXED)

`two_step_hard_delete` asserted the receipt (`rows_deleted == 1`) against a
genuinely seeded episode, which DOES discriminate the P0 — under the bug the
scoped scan matches nothing and reports 0. But every assertion read the
handler's own report of what it did, so a handler that reports a delete it never
performed passed. Step 4 now re-targets the deleted id and requires 404, the
contract `unknown_id_returns_404` already pins. Mutation-verified against a live
row.

### S10 — 12 of 15 python guards ran in no workflow (FIXED)

`scripts/tests/` holds 15 stdlib guards; workflows named three. The other
twelve — 66 passing assertions covering the hook adapters, capture signal gate,
contextd lifecycle and scope forwarding, turnkey verification, the Moon identity
probe and the session digest — executed nowhere. Not failing quietly; not
running. All 15 pass under `env -i` with an empty HOME, so wiring cost nothing.

ci.yml now discovers them by glob rather than listing three by name (a
hardcoded list is how the gap opened), and `test_gated_tests_have_a_runner.py`
— which existed to catch exactly this shape and did not police its own
directory — now asserts every guard has a runner, with a vacuity floor.

Two first-draft errors worth keeping: the RED passed because a *comment* in
ts-prebuild.yml ("No workflow ran scripts/tests/*.py before 0.6.1") satisfied a
presence check; and the first mutation was invalid because `unittest.main()`
exits before an appended `raise` runs, which nearly read as "the loop cannot
detect failures".

### S11 — nothing checked that npm entry points get published (FIXED)

`files` is an allowlist; anything absent is silently omitted from the tarball.
A package can declare `"require": "./lunaris.cjs"`, pass every test, publish,
and then throw MODULE_NOT_FOUND on first `require()`. Nothing packs a tarball
and inspects it, so `files` was the only thing standing in the way — and the
v0.6 rewrite had just added two new entry filenames by hand. Now ratcheted in
`test_npm_version_parity.py`, mutation-verified both ways (drop a file from
`files`; point an export at a nonexistent path).
