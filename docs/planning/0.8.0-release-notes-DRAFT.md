# Lunaris 0.8.0 — release notes (DRAFT)

**Status: draft, not published.** Covers the 59 commits between `v0.7.1` and
`origin/main` (20 fix / 13 feat / 12 test / 9 docs / 2 chore / 1 style / 1
spike / 1 ci). This file is written to sit alongside the `[Unreleased]`
section of `CHANGELOG.md` — that section already has real prose for most of
this work in the project's own voice; this draft folds in what it does not
yet cover (the degraded-embedder visibility work, the F41/F43/F22 fixes, and
the known-limitations section) and reorganizes around what a reader upgrading
from 0.7.1 needs to know, in order.

In 0.x land, per `RELEASE.md` §2, any minor bump is "breaking allowed."
0.8.0 uses the bump anyway, on the one real signature break below — 0.7.x's
own precedent (0.7.0, 0.6.2) is to call these out explicitly rather than bury
them in a patch note.

---

## Highlights

- **The direct-capture write path is available.** `memory.remember` (MCP) and
  its SDK/CLI equivalents let an agent or operator write a decision, fix,
  preference, or constraint straight into memory, and `memory.profile`
  renders what a scope actually holds as a readable page. See
  [**What this release does *not* claim**](#what-this-release-does-not-claim)
  before you read that as more than it is.
- **One breaking change.** `lunaris_core::audit::Publisher::publish` and
  `publish_audit_event` gain a leading `&Scope` parameter. Source-level only —
  no wire format change, no data migration. See
  [Breaking change](#breaking-change-publisherpublish-takes-a-scope).
- **Per-scope retention**, exposed on every surface (engine, MCP, Python,
  TypeScript): a scope can set `{ max_age_ms, hard }` and sweep rows past
  that age. Opt-in per scope; nothing is swept by default.
- **The audit trail is readable, not just writable.** `audit_events(from,
  to, limit)` returns a scope's own history non-destructively; dropped
  events are now a Prometheus counter instead of a silent gap.
- Two real bugs fixed in the read path most people hit first: a scoped
  as-of/scratchpad read that queried the wrong partition (F41), and an
  activation-ranking prior that was mathematically inert in production
  (F43) — both detailed under [Fixed](#fixed).

## Breaking change: `Publisher::publish` takes a `&Scope`

**Who this affects:** anyone implementing the `lunaris_core::audit::Publisher`
trait directly, or calling `publish_audit_event` outside this workspace.
SDK, MCP, HTTP, and CLI callers are unaffected — no consumer-facing API
changed shape.

**Why:** the old signature had no scope, so the blanket `impl Publisher for
Arc<dyn StoragePort>` used `Scope::dev()` for every audit event regardless of
which tenant produced it — forget receipts, consolidator promotions and
archives, verifier arbitrations, reflect invalidations, all filed under one
shared partition. A tenant reading their own audit stream saw nothing for
operations that definitely happened, and anyone who could read `dev` could
read everyone's receipts. This is the hard prerequisite for a tenant-scoped
audit-read API.

**Before (0.7.1):**

```rust
#[async_trait]
pub trait Publisher: Send + Sync {
    async fn publish(
        &self,
        topic: &str,
        partition: u16,
        payload: Bytes,
    ) -> Result<u64, PublishError>;
}
```

**After (0.8.0):**

```rust
#[async_trait]
pub trait Publisher: Send + Sync {
    async fn publish(
        &self,
        scope: &Scope,
        topic: &str,
        partition: u16,
        payload: Bytes,
    ) -> Result<u64, PublishError>;
}
```

`publish_audit_event` picks up the same parameter as its new second
argument. Add the scope you already hold at the call site — every one of the
six production call sites in this repo already had one available. No data
migration and no wire-format change: this only affects code that calls the
trait directly.

## Added

- **Per-scope retention (engine + MCP + Python + TypeScript).**
  `ScopedLunaris::{retention_policy, set_retention_policy, enforce_retention,
  preview_retention}` plus `*_at` variants for a pinned cutoff. A policy is
  `{ max_age_ms, hard }`; a scope with no policy is never swept, and a policy
  that fails to parse is an error rather than a silent no-op (`None` already
  means "keep everything"). A sweep runs through the same scoped `forget`
  path as a human-initiated delete, so it inherits soft/hard semantics, the
  chunk sweep, and the audit receipt — a hard sweep still goes through the
  confirmation-token rail. MCP adds two tools (`memory.retention`,
  `memory.retention_enforce`, the latter previewing by default, same ruling
  as `memory.forget`); Python and TypeScript get the same four operations.
  Lunaris does not schedule sweeps itself — that stays the embedding host's
  job.
- **The audit trail can be read back.** `ScopedLunaris::audit_events(from_ms,
  to_ms, limit)` returns a scope's own decoded `AuditEvent`s without
  consuming them (this is a read over the underlying stream, not the
  `subscribe` consumer, so it cannot be run once and drain a live
  subscriber). Entries that fail to decode are counted rather than dropped
  silently. `memory.status` now also probes the audit topic itself, in
  addition to the three worker-backlog topics it already reported.
- **Dropped audit events are countable.** `audit_events_dropped()` in
  `lunaris-core`, exported by `lunaris-server` as
  `lunaris_audit_events_dropped_total` on `/metrics`. Fire-and-forget publish
  is unchanged — a broker hiccup still must not roll back a committed
  `forget` — but the loss is now visible instead of indistinguishable from
  "it did not happen."
- **`memory.remember` — direct-capture write path (MCP, hook, SDKs).** One
  tool, four closed kinds: `decision`, `fix`, `preference`, `constraint`.
  Content is stored as readable prose, not a JSON envelope, and is filed
  under `source = "{kind}:{scope}"` so `filters.source_prefix="fix:"`
  retrieves only fixes.
- **`memory.profile` — render what a scope has captured.** A pure read (no
  writes, no LLM summarization) that groups captured knowledge by kind,
  most-durable-first, and excludes raw tool-call telemetry so a
  mostly-telemetry store doesn't render a page that looks informative and
  isn't. An empty scope renders an explicit "nothing captured yet" page.
- **A degraded embedder now announces itself instead of waiting to be
  asked.** Rust callers already had `resolved_embedder_backend()`; Python
  and TypeScript callers had no way at all to ask (`grep -rn degraded
  crates/lunaris-{py,ts}/src` returned nothing before this release), so a
  silent fallback to `NoopEmbedder` — every vector zeroed, recall still
  "succeeding," results still plausible-looking — was invisible from a
  `pip install lunaris` / `npm i lunaris` process. Both SDKs now expose
  `embedder_backend()` → `"llamacpp" | "openai-remote" | "ollama-remote" |
  "noop" | "unresolved"`. Separately, `Lunaris::open` in Rust now emits a
  one-time stderr warning when it falls back to `noop` and nothing else is
  already collecting `tracing` output — set
  `LUNARIS_SUPPRESS_DEGRADED_WARNING=1` to silence it. This closes the open
  half of the 0.7.x embedder-visibility work (PR #200); it does not change
  ranking or make the fallback itself less lossy.
- **`lunaris-integrations` is publishable to PyPI**, with CI building the
  sdist/wheel and running its full test suite (18 tests, none of which had
  ever run in CI before this release) against every framework extra.
- **One GGUF model catalogue and one stager**, replacing two independent
  download-verify-rename implementations that had drifted (`lunaris-mcp` and
  `lunaris-cli` each had their own). `LUNARIS_MODELS_DIR` now relocates both
  the staging target and the engine's own model lookup together.
- **`lunaris repair-vectors` CLI command** (see [Fixed](#fixed) below) —
  previews by default, `--commit` to apply, scoped, idempotent.

## Fixed

- **A scoped as-of / scratchpad read searched the wrong partition (F41).**
  `AsOfScratchpad::read` (and the identical bug in `CodingSessionMemory`'s
  fallback) built its read against the default `Scope::dev()` handle instead
  of the scope the caller actually wrote to, and matched on path *prefix*
  rather than exact equality — so `read("notes")` could also return
  `notes-old`. Both are now scoped correctly and matched exactly.
- **The time-travel read then returned rewritten, stale, or unreadable
  content (F42), once F41 stopped it returning nothing.** Three distinct
  defects, all confirmed on a live store: chunk text is a lossy,
  smart-punctuation-normalized projection of what was written; every
  version of a key stayed indexed and got concatenated onto the answer; and
  a handful of paths (`big`, `state`) made the read fail outright with an
  empty-query error. Both callers now route through one `WorkingMemory`
  read that recovers the value verbatim from its parent record and resolves
  to exactly one version.
  **Behavior change on one path:** `WorkingMemory::read`'s ranked fallback
  (used when the newer source-index sidecar is missing) previously returned
  the top-*ranked* hit, which is not necessarily the newest one. It now
  returns the newest version. A `memory.scratchpad_read` caller relying on
  that fallback may see a different (correct) value after upgrading.
- **The activation-ranking prior was mathematically inert (F43).** The
  ACT-R-derived boost clamped to zero for any memory older than roughly
  `weighted_references²` seconds — 9 seconds after one reference, about 15
  minutes after ten — so in practice it never fired. Replaced with a
  logistic curve that stays positive across the full age range. **This
  changes result ordering** on every recall surface that uses it (MCP,
  contextd, the Claude Code hook, `lunaris-cli`, HTTP `/v1/recall`, and the
  Rust/Python/TypeScript SDKs as of the same release) — recall now favors
  previously-referenced memories, which is the feature's original intent,
  landing for the first time. `LUNARIS_ACTIVATION_BOOST=0` remains the
  opt-out. **No published benchmark number is affected**, because
  `lunaris-bench` does not populate the activation ledger, so the boost
  reads as `0.0` on both sides of this fix in every gauntlet run.
- **622 of 1,235 chunk rows in the live store carried an all-zero embedding
  vector that scored as a near-universal KNN match** rather than as an
  unindexable row — measured at cosine 0.500, ranking above a genuine
  cosine-0.3 hit. A write-side guard from a prior release stopped new rows
  from doing this, but nothing repaired rows already written between
  2026-07-20 and 2026-08-22. `lunaris repair-vectors --scope <s> [--commit]`
  sweeps and strips the `vec` field from affected rows (content and BM25
  text are untouched, so a later re-embed has something to write back into).
- **Errors were silently mislabelled across four independent classification
  sites.** `LunarisError::Scope` fell through to the generic wildcard arm in
  the Prometheus metric label, the HTTP status map, and both SDKs' error
  codes, because `LunarisError` is `#[non_exhaustive]` and none of the four
  downstream match statements could be checked for exhaustiveness by the
  compiler. Classification now lives once, in `lunaris-core`, where
  exhaustiveness *is* enforced; the four call sites consume it instead of
  re-deriving it.
- Assorted CI/bench reliability fixes that were masking their own targets:
  the perf-bench opt-in flag could never actually be opted into; the
  latency-budget suite could only ever report success regardless of the
  measured value; and Moon builds for the latency gate looked for the
  binary somewhere `MOON_BINARY` did not point. None of these change
  runtime behavior; they change whether CI would have caught a regression.

## Changed

- **Raw tool-call telemetry is no longer injected into agent context by
  default.** It is still captured and still returned by `memory.recall` —
  it's substrate, not context — but the hook stops auto-injecting it at any
  phase. A census of a live store's injection history found 99.9% of
  everything ever injected was a raw tool call, against two curated entries
  in the entire history. Set `LUNARIS_CONTEXT_INCLUDE_TOOLCALLS=1` to restore
  the old behavior.
- **The agent installer (`scripts/setup-lunaris-agents.py`) is now the
  headline install path** in the README, because it is the only one that
  ends with a working store — it installs and starts Moon itself when none
  is found. The old `claude mcp add` one-liner wires an MCP server against a
  Moon it never creates.

## What this release does *not* claim

`memory.remember` and `memory.profile` make direct capture *possible*. They
do not make it *happen*. Nothing in Lunaris, its hooks, or its MCP server
calls `memory.remember` on an agent's behalf — that wiring (an agent-facing
skill that decides *when* something is worth remembering) is explicitly
scoped to the next milestone, not this one.

Measured on the production store on 2026-08-27, across 303,874 episodes:
**zero real curated memories**. The five non-`lunaris:tool_call:*` sources
found are test fixtures. If you install 0.8.0 and query your own store today,
you will find raw tool-call history, not a curated memory — that is expected,
and it is the honest state of this release. `memory.profile` exists in part
to make that visible rather than papered over: an empty scope renders a page
that says "nothing captured yet" naming `memory.remember`, not a blank page
that could be mistaken for "nothing to see."

`lunaris-integrations` is **not on PyPI**. Its publish workflow exists, but its
first run is gated on a PyPI token scoped to the `lunaris` project, so
`pip install lunaris-integrations[langgraph]` — which `docs/POSITIONING.md` and
the book's why-lunaris page both suggest — does not resolve. Use the adapters
from a source checkout of `integrations/` until that first publish lands.

## Performance

Every number below names its operating point. `fast` (cross-encoder rerank
OFF) is the shipped default; `quality` (rerank ON, opt-in via
`LUNARIS_RECALL_RERANK=1`) is roughly two orders of magnitude slower and is
never the implicit baseline for a claim — see
[`docs/benchmarks/operating-points.md`](../benchmarks/operating-points.md).

From CI run `32506983470` (N=40, two-arm LongMemEval ratchet, zero errored
questions on either arm):

| Operating point | Rerank | Any-gold hit rate (J) |
|---|---|---|
| `fast` (shipped default) | OFF | **97.5%** |
| `quality` (opt-in) | ON | **100.0%** |

`quality` answers exactly the one question `fast` misses out of 40 — a
single attributable delta, not noise. `fast` reproduced the same-seed
Darwin-arm64 baseline exactly (identical single miss) on an independent
Linux x86 run.

Backup/restore: **RPO = 0, RTO < 1s**, measured via the drill in
`scripts/release/rollback-drill.sh`.

No PersonaMem or LongMemEval N=125 numbers changed in this release; the
N=125 two-operating-point republish is tracked separately and needs an
owner-held API key.

## Known limitations

- **F26 — a KNN prefilter Moon cannot parse degrades to *no filter* rather
  than an error.** Moon's vector-search prefilter parser (distinct from its
  full FT.SEARCH range parser) fails to parse an exclusive-bound expression
  like `"(200"` and falls through to an *unfiltered* search — silently
  returning more rows than asked for rather than erroring. This is
  Moon-side: fixed upstream on Moon's `main` branch (closed as `moon#648`),
  but not present in any released Moon build as of this writing (`v0.8.5`,
  `v0.8.6`, and `v0.8.7` all lack the fix; Lunaris vendors a pre-fix
  commit). Lunaris works around it by encoding exclusive upper bounds as
  `hi - 1` rather than `(hi` on every render path, verified by CI against a
  live Moon, with a reverse ratchet that will fail loudly the day the
  vendored Moon version picks up the real fix (so the workaround does not
  outlive its reason silently). **This is a recall-correctness defect, not
  a cross-tenant isolation issue** — Moon scopes data by index name, not by
  filter predicate, so a dropped filter over-returns *within* a scope and
  cannot leak across scopes.

- **R5 — resolved before the tag: `Navigate` is sound; its test was not.**
  A live-Moon test (`filtered_navigate_never_leaks_foreign_source_moon`) had
  been failing on its discriminator assertion, and no CI workflow had ever run
  `-p lunaris-retrieve`, so it gated nothing. Investigation found the operator
  correct and the fixture degenerate: it wrote 2 documents and asked for `k=2`,
  making every document a seed. Moon excludes seeds from graph expansion by
  design, so the expected row returned at hop depth 0, and `Navigate`'s
  documented `hop_depth >= 1` filter — hop-0 rows are seeds, never payload —
  correctly dropped it. **No `Navigate` behaviour changed; zero `src/` files
  were touched.** The fixture was corrected, `-p lunaris-retrieve` is now wired
  into CI behind a strict-skip guard, and the filter-leak assertion that had
  never once executed now runs and passes: a filtered `Navigate` does not leak
  foreign-source results.

  One related limitation remains open and is worth knowing: Moon's `k` is a
  **final** result cap, not a seed cap, and hop-0 seeds occupy slots that
  Lunaris then discards. `Navigate::new("entities", k)` therefore returns
  *fewer than* `k` facts — always at least one slot, more when several seeds
  score closely. That is recall headroom, not a correctness fault.

- **The Postgres/SQLite as-of read gap (STORE-07), the audit MQ topic's
  unbounded growth (no Moon `TRIM`/`MAXLEN`), and hard-`forget` leaving
  facts/entities/relations un-swept** all carry over unchanged from prior
  releases — see the [0.7.1](../../CHANGELOG.md#071--2026-08-25) and
  [0.7.0](../../CHANGELOG.md#070--2026-08-18) changelog entries for detail.

## Upgrade notes

- If you implement `lunaris_core::audit::Publisher` or call
  `publish_audit_event` directly: add the `&Scope` argument. Everyone else
  is unaffected.
- If you rely on `LUNARIS_ACTIVATION_BOOST` being effectively a no-op: it
  no longer is. Recall ordering on every surface will shift toward
  previously-referenced memories. Set `LUNARIS_ACTIVATION_BOOST=0` if you
  need the old (near-inert) ordering back, with the caveat noted under
  [Fixed](#fixed) for very recently referenced memories.
- If you set `LUNARIS_CONTEXT_INCLUDE_TOOLCALLS` (or its older alias
  `LUNARIS_CONTEXT_PROMPT_INCLUDE_TOOLCALLS`) expecting raw tool calls in
  context, you're unaffected — that's what turns the old behavior back on.
  If you didn't, and relied on prior tool-call context appearing
  automatically, it no longer does.
- No data migration is required for any change in this release, and no schema
  version to bump. Rolling 0.8.0 back to 0.7.1 on the same Moon store is
  supported in place. **Rehearsed 2026-08-27**, both directions plus a
  roll-forward, with `scripts/release/moon-inplace-rollback-drill.sh` — the
  0.7.1 binary read back the episode 0.8.0 wrote.
- Audit events now publish under the producing scope's MQ topic
  (`lunaris:{scope}:__lunaris_audit__`) rather than `lunaris:dev:…`. Older
  events are neither lost nor migrated: they remain in the `dev` topic. Nothing
  could read them before — `audit_events` is new here — so `audit_events` shows
  history starting at your upgrade rather than an empty trail. To reach older
  events, read the `dev` scope, and treat what you find as cross-tenant.

## Internal / not user-facing

This release also includes CI and test-harness hardening that changes no
runtime behavior but is worth naming for completeness: cross-SDK embedder
parity testing made bit-exact and CI-runnable; the book's Rust code fences
(54 of them) now actually compile in CI, which surfaced and fixed four
doc/example drift bugs; a Cypher write-scan performance regression
(`INGEST-06`) is now pinned by a test rather than silently possible to
reintroduce; and several release-tooling fixes (TS lockfile integrity
hashes, an npm-publish-gate false negative, `bump-version.sh` missing
napi's generated loader). None of these change any documented behavior,
default, or API.
