## Headline — full N=500 dataset

An earlier draft of this doc reported an N=50 subsample (98.0%, 49/50) and
described it as beating Zep. **That was a sampling artifact, not the real
number.** `longmemeval_s` orders its questions with an easy, mostly
single-session-factual prefix; q0-49 is not representative of the full
500-question set, where multi-session counting/aggregation questions
(clustered around q70-140 and scattered later) are materially harder. The
real result, run over the complete dataset, is below.

| Metric | Score |
|---|---|
| **Retrieval — any gold session surfaced (`evidence_recall_hit`)** | **98.2% (491/500)** |
| **Retrieval — all gold sessions surfaced (`evidence_recall_all`)** | **93.0% (465/500)** |
| **End-to-end J-score** (MiniMax m3 as both generator and judge) | **85.4% (427/500)** |
| Zep (published) | 90.2% |
| Mem0 (published) | 66–68% |

**Read this honestly, not defensively:**

- Retrieval quality itself is strong and holds at full scale — it does not
  degrade from the N=50 subsample's implied quality.
- The end-to-end J-score (85.4%) is *below* Zep's published 90.2%. Lunaris
  does not currently beat Zep on this metric at full-dataset scale. It does
  beat Mem0's published 66–68%.
- **The Zep/Mem0 rows are not a controlled comparison.** J-score conflates
  retrieval quality with the reader/judge model's reasoning. This run used
  MiniMax m3 as *both* the generator and the judge; Zep's published number
  used a different (and generally stronger, per the LongMemEval paper)
  reader. A fair head-to-head requires holding the reader model constant
  across systems, which this run does not do.
- Lunaris's actual contract (see project `CLAUDE.md`) is sub-25ms
  *recall* correctness, not end-to-end QA accuracy — the retrieval-only
  rows are the more direct measurement of that contract.

## Miss breakdown (73 misses out of 500)

| Category | Count | What it means |
|---|---|---|
| Reader/generation reasoning gap | 48 | `evidence_recall_all = true` (gold sessions fully retrieved) but the generated answer was still wrong — dominated by multi-session counting/aggregation questions where the reader double-counted or misclassified the question type. |
| Genuine retrieval gap | 23 | `evidence_recall_all = false` — at least one gold session never surfaced in the top-60 pool. |
| Harness transport error | 2 | q89, q255 — HTTP POST to the local MiniMax route_shim failed after all 3 retries (transient network/shim issue). Correctly counted as misses per the harness's design-for-failure policy (never silently exclude a failure); not a model-quality or retrieval issue. |

The reader-reasoning-gap bucket is the largest by a wide margin (48/73,
~66% of all misses). Two concrete instances in this bucket were
root-caused and fixed (red/green TDD, not yet merged to `main`) on
`fix/lme-harness-counting-classifier` (`4fffcc4`):

1. `classify_intent()` in `crates/lunaris-bench/src/eval/lme_judge.rs`
   misrouted bare "how many day/week/month/year" tally questions into
   `Temporal` (duration) handling instead of `Counting`, unless a genuine
   two-point-in-time connective (`between`/`since`/`until`/`before`/`after`)
   was present.
2. `Counting`'s generation prompt had no instruction to deduplicate a
   single real-world event mentioned across more than one session
   (planned, then recapped) — the model counted it twice.

These two fixes address a subset of the reader-reasoning-gap bucket; the
remaining instances and the full 23-question retrieval-gap bucket are
unaddressed and would need further investigation before another full rerun
to measure the actual score delta.

## Methodology — why one process per question

Each question is run as its **own OS process**
(`LUNARIS_EVAL_LME_OFFSET=$off LUNARIS_EVAL_LME_LIMIT=1`), with a
`redis-cli flushall` before every question. This is load-bearing, not
incidental: running many questions in a single long-lived process hits a
documented Candle Metal activation-buffer leak that silently degrades
scores after roughly question 30. All figures in this doc use the
per-question-isolated harness; do not compare against a single-process run.

For this N=500 run, score distributions were spot-checked at several
points across the run (q262-264, q300-303, and around a ~4h11m gap at
q466→q467 caused by the machine sleeping overnight) to confirm no
recurrence of the degradation signature — genuine small-magnitude varied
cosine scores throughout, and q467's result was clean and uncorrupted after
the sleep gap.

Exact per-question invocation:

```bash
redis-cli -p 6381 -t 3 flushall
RUST_LOG=warn MOON_URL="moon://127.0.0.1:6381" \
  LUNARIS_EMBEDDER_GGUF="$HOME/.lunaris/models/granite-embedding-311m-multilingual-r2.Q4_K_M.gguf" \
  LUNARIS_RERANKER_GGUF="$HOME/.lunaris/models/bge-reranker-v2-m3.Q5_K_M.gguf" \
  LUNARIS_EMBEDDER_DIR="$HOME/.cache/lunaris/models/granite-embedding-311m-multilingual-r2" \
  LUNARIS_RERANKER_DIR="$HOME/.cache/lunaris/models/bge-reranker-v2-m3" \
  LUNARIS_EVAL_LME_DATASET="longmemeval_s" LUNARIS_EVAL_LME_JUDGE=1 LUNARIS_EVAL_LME_RERANK=1 \
  LUNARIS_EVAL_LME_GEN_MODEL="minimax-m3:cloud" LUNARIS_EVAL_LME_JUDGE_MODEL="minimax-m3:cloud" \
  LUNARIS_EVAL_OLLAMA_URL="http://127.0.0.1:21434" \
  LUNARIS_EVAL_LME_HYBRID=1 LUNARIS_EVAL_LME_POOL=40 LUNARIS_EVAL_LME_TOPK=60 LUNARIS_EVAL_LME_ADAPTIVE=1 \
  LUNARIS_EVAL_LME_OFFSET="$off" LUNARIS_EVAL_LME_LIMIT=1 LUNARIS_EVAL_LME_DEBUG=1 \
  LUNARIS_EMBED_BATCH=8 \
  target/release/lunaris-evals longmemeval --output "q${off}.json"
```

`LUNARIS_EMBEDDER_DIR` / `LUNARIS_RERANKER_DIR` must point at the operator's
actual staged-weights directory (`~/.cache/lunaris/models/<name>/` on this
box) — the built-in default (`dirs::cache_dir()`,
`~/Library/Caches/lunaris/models/` on macOS) silently falls back to a
zero-vector Noop embedder/reranker (WARN-only, no hard failure) if the
directory is empty.

## Reproduction checklist

1. Build release: `cargo build --release -p lunaris-bench --features embedder-gguf,reranker-gguf -p lunaris`.
2. Stage the two GGUF weights (`stage-models` binary or manual download) under `~/.lunaris/models/`.
3. Bring up a fresh Moon on 6381 (`--appendonly no --disk-free-min-pct 1`).
4. Point an Ollama-compatible chat endpoint at MiniMax (or any OpenAI/Ollama-chat-compatible model) via `LUNARIS_EVAL_OLLAMA_URL`.
5. Loop `off` from 0 to 499 at the **shell level**, one `lunaris-evals longmemeval` invocation per offset — never `LUNARIS_EVAL_LME_LIMIT=500` in a single process.
6. Tally `correct=true` lines across all 500 logs — **and** treat any log containing `judge error`/`counted miss` (a transport failure, not a `correct=` line) as an additional miss. A tally that only greps `correct=(true|false)` will silently undercount.
