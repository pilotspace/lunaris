# Recall round-trip collapse — HMGET + concurrent hydration A/B (2026-06-10)

Quick task `260610-f91` removed the serialized storage round trips from the
recall hot path. This note records the A/B methodology and numbers so the
claims in `docs/ARCHITECTURE.md` ("The numbers that anchor the claims") stay
falsifiable.

## What changed (commits `ab4210c..637dc4c`)

| Site | Before | After |
|---|---|---|
| `lunaris-storage-moon::kv::read_as_of` | 2 serial `HGET`s (`v`, then `bt`) per key | 1 `HMGET key v bt` |
| `lunaris-retrieve::hydrate::hydrate` | 1 awaited `read_as_of` per hit, serial | ordered `buffered(32)` fan-out (chunks) + `buffer_unordered(32)` (episodes) |
| `lunaris-retrieve::hydrate::partial_hydrate_text` (rerank feed) | serial per-candidate | ordered `buffered(32)` fan-out |
| `lunaris-storage-moon::kv::scan_range` | 1 serial `HGET` per SCAN match | per-batch `buffered(32)` fan-out |
| `ThenRetriever` | re-ran the query embedding for the narrowed context | seeds the child `OnceCell` from the parent |

Concurrent in-flight requests pipeline over the shared
`redis::aio::MultiplexedConnection`, so a recall-with-rerank that previously
paid ~120 sequential round trips now pays a handful of pipelined batches.
Hit ORDER is preserved (ranked results), missing-row skip semantics are
unchanged, and storage errors still propagate (guarded by
`crates/lunaris-retrieve/tests/hydrate_concurrent.rs`).

## Methodology

- Harness: `scripts/bench-mcp-stdio.py` with the recall `k` patched 5 → 30
  (`sed 's/"k": 5}/"k": 30}/'`) so hydration dominates the storage budget.
- Backend: one live native Moon (`--shards 1`, loopback `127.0.0.1:6380`),
  shared by both runs; scope-isolated indices (`bench-base` / `bench-head`).
- Binaries: `lunaris-mcp` release at `599d5c2` (pre-optimization) vs `637dc4c`
  (optimized), baseline built from a worktree against the identical
  `vendor/moon` pin.
- Workload: 120 unique-content ingests, then 200 `memory.recall` calls at
  k=30 over 5 rotating queries (after warmup every query embedding is cached,
  so recall latency ≈ FT.SEARCH + hydration — the paths under test).
- Embedder: granite-311m Q4_K_M GGUF, in-process.

## Results — `memory.recall` (n=200, k=30, avg hits/query 30.0 on both)

| metric | base `599d5c2` | optimized `637dc4c` | delta |
|--------|---------------:|--------------------:|------:|
| p50    | 12.0 ms | **6.0 ms** | −50% |
| p95    | 39.6 ms | **6.1 ms** | −85% |
| p99    | 97.3 ms | **6.2 ms** | −94% |
| max    | 261.2 ms | **8.3 ms** | −97% |
| mean   | 16.6 ms | **6.0 ms** | −64% |

The headline is the tail: a chain of ~60+ serial awaited round trips amplifies
every scheduler hiccup into the p95/p99; pipelined batches do not. Post-change
the k=30 distribution is essentially flat (p50 ≈ p99 ≈ 6 ms), sitting inside
the 25 ms contract with 4× headroom at the tail.

Run order was baseline first, optimized second — the Moon instance held MORE
total keys during the optimized run, so accumulation bias, if any, works
*against* the optimized numbers.

## Relationship to the v0.2.x strict-replay numbers

> **Superseded (2026-08-21).** This section originally named the 2026-04-23
> strict-replay figure as "the anchor for the sub-25 ms contract". It is not,
> and was retracted repo-wide: that run used Ollama + EmbeddingGemma 300M at
> k=3 on a 10k corpus — a stack deleted in v0.4 (Ollama) and again in v0.6
> (candle) — and its methodology page was never populated with captured
> numbers. **The contract's anchor is the GA-2b envelope**
> ([`capacity.md`](../operations/capacity.md)): p50 19.2–22.4 ms /
> p99 23.4–24.4 ms at 100k documents per scope.

The 2026-04-23 run measured a different harness at a smaller k. This A/B is a
*relative* measurement isolating the hydration/storage path at k=30, where the
serial round trips dominated — the relative result (the tail no longer scales
with k) stands on its own and does not depend on the retracted absolute.
