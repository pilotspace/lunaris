# v0.4 release-binary-size gate

N-04 D4 — keep `target/release/lunaris-server` lean.

## Budget

| Metric                             | Value      |
|------------------------------------|------------|
| Baseline (2026-05-15, post-N-03)   | **27 MiB** |
| Ceiling (CI fails above this)      | **35 MiB** |
| Headroom                           | **8 MiB**  |

The 8 MiB headroom absorbs a single medium-sized dependency addition
(e.g., a new HTTP middleware crate) before forcing the budget to be
re-evaluated. Anything larger requires:

1. A justification line in the PR description.
2. A bumped `CEILING_BYTES` constant in
   `crates/lunaris-bench/tests/binary_size_gate.rs` with a comment
   explaining what crossed the budget.
3. Updated baseline + ceiling rows in this doc.

## Measurement procedure

```sh
# Build the release binary.
cargo build --release --workspace --exclude lunaris-py --exclude lunaris-ts

# Inspect the size.
ls -la target/release/lunaris-server

# Run the gate (asserts ≤ 35 MiB).
./scripts/check-binary-size.sh
```

The wrapper invokes:

```sh
cargo build --release -p lunaris-server
cargo test -p lunaris-bench --features ci-perf-gates --release \
    --test binary_size_gate -- --include-ignored --nocapture
```

Plain `cargo test --workspace` skips the gate (the
`ci-perf-gates` feature is off by default) so dev boxes that have
never built `--release` don't see a stale-binary failure.

## Why a feature flag, not always-on?

The gate reads `target/release/lunaris-server` directly. If that path
doesn't exist, the test panics — useful in CI (the operator just
forgot the `cargo build --release` step) but noisy on dev boxes
running a bare `cargo test`. The `ci-perf-gates` feature is the
explicit opt-in for any size / latency gate that depends on a
release artifact.

## Remediation when the gate fails

1. Identify the new dependency / code path that crossed the budget.
2. Check whether it's load-bearing: can it be feature-gated? Is there
   a leaner alternative?
3. If the addition is justified, bump `CEILING_BYTES` AND the table
   above in the same commit, with a PR description that names the
   crate / feature responsible.

History — bumps to the ceiling are intentionally rare. The baseline
will drift downward as `lto = "fat"` + `codegen-units = 1` + `strip`
mature; the ceiling moves only on real growth.
