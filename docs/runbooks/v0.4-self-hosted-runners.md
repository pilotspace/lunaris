# v0.4 — Self-hosted runners for perf-gates (Operator Runbook)

O-03 Deliverable E. The release-blocker that the engineer who built O-03
A–D cannot run themselves: provision the two self-hosted GitHub Actions
runners that make `perf-gates.yml` actually enforce the absolute
hardware-target gates from
`.planning/milestones/v0.4-NATIVE-SINGLE-BACKEND/HARDWARE-OPTIMIZATION-ROADMAP.md`.

**Owner:** Lunaris on-call operator.

**Pre-flight:**
- `perf-gates.yml`, `perf-baseline-save.yml`, and the
  `perf-gate-check` binary must be merged to `main` (O-03 A–C).
- `docs/benchmarks/v0.4.x/README.md` must be merged (O-03-D).

This runbook covers ONLY the operator infra work. The harness side is
done; without these runners the workflows queue forever and the
absolute gates remain TBD.

## 1. Hardware requirements per matrix cell

| Matrix cell        | Provisioning   | Min spec                                                    | Approx monthly cost |
|--------------------|----------------|-------------------------------------------------------------|---------------------|
| `apple-metal`      | Self-hosted    | M2 Pro 10-core, 16 GB unified memory, macOS 14.x, 256 GB SSD | $200 (Mac Mini M2 Pro depreciated over 36 mo) |
| `cuda-sm80`        | Self-hosted    | NVIDIA A10 / A100 / RTX 30/40-series (sm_80+), 24 GB VRAM, Ubuntu 22.04, 64 GB system RAM | $400 (AWS g5.xlarge spot equivalent) — or $0 if reusing an existing GPU dev box during off-hours |
| `cpu-x86_64-mkl`   | GH-managed     | `ubuntu-latest`                                             | $0 (free tier)      |
| `cpu-aarch64-neon` | GH-managed     | `ubuntu-22.04-arm`                                          | $0 (free tier when available; else self-host on Graviton t4g.medium ≈ $25/mo) |

Two self-hosted boxes total: one Mac, one CUDA host. The GH-managed
cells need no provisioning.

### Cost note

The two self-hosted runners are the marginal v0.4 infra cost. At ~$600/mo
they're cheap relative to engineer time saved by catching perf
regressions automatically. Spot/burst options:

- **Mac**: a single Mac Mini M2 Pro one-time purchase ($1,399 retail) > 36
  months ≈ $40/mo amortized. Bare-metal beats cloud Mac pricing by 5×.
- **CUDA**: a dev box already running a GPU for training can host the
  runner as a sibling user — set up `Restrict to: lunaris-perf-bench`
  label so the runner doesn't steal GPU cycles during business hours.

## 2. GitHub runner registration

Per-host steps (do this twice — once per self-hosted cell).

### 2.1 Create the runner registration token

1. Go to repo → Settings → Actions → Runners → New self-hosted runner.
2. Pick the OS (macOS / Linux).
3. Copy the `--token` value. **This token expires in 1 hour.** Use it
   immediately on the host.

### 2.2 Install on the Mac (apple-metal)

```sh
# As the dedicated runner user (NOT root, NOT your personal account).
sudo dscl . -create /Users/ghrunner
sudo dscl . -create /Users/ghrunner UserShell /bin/zsh
sudo dscl . -create /Users/ghrunner UniqueID 600
sudo dscl . -create /Users/ghrunner PrimaryGroupID 20
sudo dscl . -create /Users/ghrunner NFSHomeDirectory /Users/ghrunner
sudo mkdir -p /Users/ghrunner
sudo chown -R ghrunner:staff /Users/ghrunner

sudo su - ghrunner -s /bin/zsh
cd ~
mkdir actions-runner && cd actions-runner

# Download the macOS arm64 runner package — version from the
# registration page (always pin a specific version, never `latest`).
curl -O -L https://github.com/actions/runner/releases/download/v2.319.1/actions-runner-osx-arm64-2.319.1.tar.gz

# Verify the SHA-256 from the registration page.
shasum -a 256 actions-runner-osx-arm64-2.319.1.tar.gz

tar xzf actions-runner-osx-arm64-2.319.1.tar.gz

# Register with the labels perf-gates.yml expects.
./config.sh \
    --url https://github.com/<org>/lunaris \
    --token <REGISTRATION-TOKEN> \
    --name apple-metal-1 \
    --labels self-hosted,macos,arm64,metal \
    --work _work \
    --unattended

# Install as launchd daemon so it survives reboots.
./svc.sh install
./svc.sh start
./svc.sh status
```

Rust toolchain (one-time):

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain 1.94
~/.cargo/bin/rustup component add rustfmt
```

### 2.3 Install on the CUDA box (cuda-sm80)

```sh
# As a dedicated unprivileged user.
sudo adduser --system --group --shell /bin/bash ghrunner
sudo mkdir -p /var/lib/ghrunner
sudo chown ghrunner:ghrunner /var/lib/ghrunner
sudo -iu ghrunner

cd /var/lib/ghrunner
mkdir actions-runner && cd actions-runner

curl -O -L https://github.com/actions/runner/releases/download/v2.319.1/actions-runner-linux-x64-2.319.1.tar.gz
sha256sum actions-runner-linux-x64-2.319.1.tar.gz
tar xzf actions-runner-linux-x64-2.319.1.tar.gz

./config.sh \
    --url https://github.com/<org>/lunaris \
    --token <REGISTRATION-TOKEN> \
    --name cuda-sm80-1 \
    --labels self-hosted,linux,x86_64,cuda \
    --work _work \
    --unattended

# systemd unit (svc.sh wraps systemctl on Linux).
sudo ./svc.sh install ghrunner
sudo ./svc.sh start
sudo ./svc.sh status
```

Rust + CUDA toolchain (one-time):

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain 1.94

# CUDA 12.x for candle-core's `cuda` feature.
# Pin the version that matches your driver via `nvidia-smi` → "CUDA Version".
sudo apt-get install -y cuda-toolkit-12-3

# Verify candle picks it up (no model load, just init).
~/.cargo/bin/cargo check -p lunaris-embed-native --features cuda
```

## 3. Secret rotation

`perf-gates.yml` and `perf-baseline-save.yml` consume one secret:
`LUNARIS_STAGE_MODELS_KEY` — an HF Hub access token with `read` scope on
`ibm-granite/granite-embedding-r2` and `BAAI/bge-reranker-v2-m3`.

### 3.1 Issuing the token

1. Sign into the Lunaris bot HF account (NOT a personal account).
2. Settings → Access Tokens → New token → Role: `read`.
3. Scope to the two repos above; do NOT grant write or org-admin.

### 3.2 Storing in GitHub Actions

```sh
gh secret set LUNARIS_STAGE_MODELS_KEY \
    --repo <org>/lunaris \
    --body "hf_xxx..."
```

### 3.3 Rotation cadence

| Trigger                              | Action                                     |
|--------------------------------------|--------------------------------------------|
| Quarterly (calendar)                 | Mint a new token, rotate via `gh secret set`, revoke the old one in HF UI |
| Suspected leak (log scrape, etc.)    | Revoke + rotate immediately                |
| Operator handoff                     | Rotate + transfer bot-account credentials  |
| HF repo gated → ungated transitions  | No-op; the token's `read` scope is unchanged |

The workflows already fail-loud if the secret is missing or invalid
(`stage-models` step prints `::error::` and exits 1 for the
baseline-save workflow; prints `::warning::` and proceeds for the
regular perf-gates workflow). No silent-skip path.

## 4. Monitoring

### 4.1 Runner health

```sh
# On each runner host, a 5-min cron checks the actions.runner service
# is alive. Alert via the team's existing Slack webhook.
*/5 * * * * /var/lib/ghrunner/actions-runner/svc.sh status || \
    curl -X POST -H 'Content-type: application/json' \
        --data '{"text":"perf-gates runner DOWN on '"$(hostname)"'"}' \
        "$SLACK_WEBHOOK"
```

Repo-side: Settings → Actions → Runners shows last-contact timestamp.
A runner that hasn't checked in for >30 min is dead — restart via
`./svc.sh stop && ./svc.sh start`.

### 4.2 Job queue depth

GitHub UI: Actions → perf-gates → queued. Sustained queue depth >2 means
a runner is stuck on a long bench (max ~15 min × 4 matrix cells = 60 min
worst case, matching the `timeout-minutes: 60` per cell in
`perf-gates.yml`).

### 4.3 Disk + cache

The runner's `_work/` dir accumulates Criterion output and Cargo target
caches. Schedule a weekly cleanup:

```sh
# Cron on each runner host, weekly.
0 4 * * 0 find /var/lib/ghrunner/actions-runner/_work -mtime +14 -delete
```

Alternative: enable Swatinem/rust-cache's automatic cleanup (already
wired in both workflows — keys are scoped per matrix cell so cache hits
are stable).

## 5. The first measurement — capturing the v0.4-O01 baseline

Once both self-hosted runners are healthy AND the GH-managed cells run
cleanly, the operator captures the first blessed baseline.

1. Confirm the absolute gates (one cell at a time): SSH into each
   runner, manually run `cargo bench --features <device> -p
   lunaris-bench --bench per_device -- --save-baseline scratch-$(whoami)`
   with the right env vars set, read the median + 99th percentile, and
   verify all numbers are inside the §2 envelope in
   `docs/benchmarks/v0.4.x/README.md`.

2. If any cell is over the absolute ceiling: STOP. File a v0.4-blocking
   regression issue. Do NOT proceed with `perf-baseline-save`.

3. If all cells are inside their envelopes:
   - Update the per-cell tables in `docs/benchmarks/v0.4.x/README.md` §3
     (replace TBD with the measured numbers + margin).
   - Open a PR with that doc change.
   - Once merged, go to Actions → `perf-baseline-save` → `Run workflow`,
     fill in `reason: "initial v0.4-O01 baseline; commit
     <sha-of-doc-pr>"`, leave `targets` at default (all 4), and run.
   - Each cell's `Verify baseline files exist` step asserts the bench
     wrote real output (not a skip-on-missing-weights).
   - The uploaded `perf-baseline-v0.4-O01-<label>` artifacts become the
     CI floor.

4. Open a follow-up PR adding `perf-bench` label to the previous one
   and re-running `perf-gates.yml`. With the baseline now in place,
   `perf-gate-check` should exit 0 against an unchanged HEAD (vacuous
   comparison). Confirm green-on-all-cells before proceeding to step 6.

## 6. Flip to required check

This is the moment perf-gates becomes a release-blocker. Do this ONLY
after §5 step 4 is green for 3 consecutive PRs (so we know the cells
are stable, not just lucky).

1. Repo → Settings → Branches → Branch protection for `main` → Edit.
2. Under "Require status checks to pass before merging", add
   `perf-gates-summary`.
3. Save.
4. Announce in `#lunaris-eng`: "perf-gates is now required on main;
   PRs with the `perf-bench` label trigger the matrix, and a >5%
   regression on any cell will block merge."
5. Remove the `perf-bench` label gate from `perf-gates.yml` `if:`
   condition if you want the workflow to run on every PR
   automatically — at that point you're paying for 4 matrix cells per
   PR open/sync; weigh against runner queue depth.

## 7. Decommissioning a runner

If a runner host is being retired:

1. Repo → Settings → Actions → Runners → Remove the runner (this
   revokes its registration token server-side).
2. On the host: `./svc.sh stop && ./svc.sh uninstall && ./config.sh
   remove --token <UNREGISTRATION-TOKEN>` (fresh token from the same
   page).
3. Wipe `_work/` (it contains repo checkouts) before reusing the host.
4. If the runner was the ONLY one in its matrix cell, the corresponding
   cell will queue indefinitely on the next perf-gates run — either
   (a) provision a replacement before the next PR opens, or (b)
   temporarily comment out that cell in `perf-gates.yml`. The runbook
   §6 required-check status will fail until the cell is restored.

## 8. Troubleshooting

| Symptom | Most-likely cause | Fix |
|---------|-------------------|-----|
| Matrix cell queues forever | No runner registered with all required labels | §2.2 / §2.3 — confirm the runner has `metal` / `cuda` label and is online |
| `stage-models` `::warning::` in `perf-gates.yml` | `LUNARIS_STAGE_MODELS_KEY` unset | §3.2 |
| `Verify baseline files exist` fails with "weights env vars unset" | hf-hub stage-models step skipped silently | Check secret is set AND has read scope on both repos |
| `perf-gate-check` exit 2 (operator error) | `target/criterion/` missing — bench didn't run | Look at the prior step's output; usually a `cargo bench` compile failure |
| `perf-gate-check` exit 1 on first run after intentional perf change | Baseline not yet refreshed | §5 + run `perf-baseline-save` workflow |
| CUDA bench fails with "no nvcc" | Toolchain drift | Reinstall cuda-toolkit pin; `nvidia-smi` must show driver >= CUDA version compiled against |

## 9. Known gaps (deferred to v0.5)

- **p99 in the relative cliff.** `perf-gate-check` gates on median
  delta only (Criterion's `estimates.json` doesn't store p99). v0.5
  TODO: post-process `sample.json` in the binary so p99 is part of the
  relative gate too. Until then the absolute p99 gate at baseline-bless
  time is the only line of defence — keep §5 step 1 tight.
- **No auto-renewal of HF token.** §3.3 is calendar-driven; if you
  forget a quarterly rotation, every PR gets a `::warning::` and
  baseline-save jobs hard-fail. v0.5 could push the rotation into a
  GH Actions scheduled workflow with `gh secret set` + a fresh token
  from a sealed HF service-account credential.
- **No bare-metal CUDA runner pricing comparison vs cloud spot.** §1's
  $400 figure is AWS g5.xlarge spot baseline; on-prem GPU dev box can
  be $0 marginal if the runner runs only during off-hours via a
  cron-gated `svc.sh start` / `svc.sh stop` schedule.
