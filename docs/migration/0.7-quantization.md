# Opt-in FT vector quantization: `?quant=` (sq8-quantization-optin, contract v1)

**Audience:** operators running Lunaris on the Moon backend (v0.3.0+) who
want to pick the vector-index recall/memory point per handle. SQLite and
Postgres backends are unaffected — `quant` is a `moon://`-only URL
parameter.

## What changed

The `moon://` URL grammar gains an optional quantization selector:

```
moon://host:port[?ws=<workspace>][&quant=<tq1|tq2|tq3|tq4|sq8>]
```

Parameter order is irrelevant; values are case-insensitive. An unknown
value fails **before any network IO** with
`StorageError::Backend("moon_invalid_quantization: …")`.

When `quant` is present, **every** FT index the handle creates — the
legacy global indices (`chunks` / `entities` / `facts` / `communities`)
AND all per-scope indices (`lunaris_{scope}_{kind}_idx`) — is created via
`FT.CREATE … QUANTIZATION <q>`. When absent, index creation is
byte-identical to previous releases (typed-SDK path, server default
**TQ4**).

## Choosing a tier

| Tier | ~bytes/vec (768-d) | Character |
|------|--------------------|-----------|
| TQ1–TQ3 | smallest | aggressive trellis quant; recall drops with tier |
| TQ4 (server default) | ~452 B | good recall on *real semantic embeddings* at 768-d+ |
| SQ8 | ~900 B | per-vector affine scalar quant; near-lossless recall |

Two practical rules from Moon's own validation:

- **≤384-d workloads should use SQ8** — TQ4 loses recall at low
  dimensions (concentration of distances + quantization noise).
- **Synthetic/random vectors make TQ4 look catastrophically bad** (the
  Lunaris eval suite measures TQ4 recall@10 ≈ 0.40 vs SQ8 ≈ 0.99 on a
  random 768-d corpus — see `tests/quantization_recall.rs`). On real
  semantic embeddings (MiniLM-class) TQ4 sits near its documented ~0.89.
  Don't extrapolate synthetic numbers to production corpora, but if your
  embedding distribution is unusual, SQ8 is the safe choice.

## Sticky-schema footgun (mirrors the dim footgun)

Quantization is fixed at `FT.CREATE` time. Moon's `FT.CREATE` is
idempotent: reopening a handle with a **different** `?quant=` against
existing indices returns "already exists" and silently keeps the old
tier. Unlike the dimension guardrail, there is **no connect-time
detection** — Moon v0.3.0's `FT.INFO` exposes no quantization probe.

To actually change tiers:

1. **(a) Reopen at the existing tier** — drop the `?quant=` change and
   keep the indices as-is; or
2. **(b) Drop and re-ingest** — `FT.DROPINDEX <name>` each affected
   index (per-scope: `lunaris_{scope}_{kind}_idx`), then reopen with the
   new `?quant=` and re-ingest from source. There is no in-place
   re-quantization path.

Also note quantization applies to **compacted** HNSW segments: vectors
in the mutable write buffer are searched at full precision until the
segment compacts (`COMPACT_THRESHOLD`, default 1000, or an explicit
`FT.COMPACT`). A freshly created index can therefore show near-perfect
recall that settles to the tier's true recall after compaction.

## SDK note

`?quant=` flows through every constructor that accepts a storage URL —
`MoonStorage::connect`, `lunaris::open("moon://…?quant=sq8")`, and the
Python/TypeScript SDK storage-URL entry points — with no new API
surface.
