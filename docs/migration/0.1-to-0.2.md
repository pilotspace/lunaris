# Lunaris 0.1 → 0.2 Migration Guide

> **Status:** **Final** — published with v0.2.0 (2026-05-11).

This guide covers the breaking changes between Lunaris **0.1.2** and **0.2.0**.
The headline change is **multi-agent / multi-tenant isolation via `Scope`** —
see [RFC 0001](../rfcs/0001-scope-newtype.md) for the full design rationale.

There is **no on-the-wire compatibility** between 0.1 and 0.2. A migration
script for existing data is tracked for the v0.2.1 patch release — for v0.2.0,
upgrade paths are: (a) drop and re-ingest from source, or (b) write a custom
script using `lunaris_core::keyspace` to rewrite KV keys with the new
`lunaris:{scope}:` prefix (Postgres backend: run migration
`20260510000005_scope_partitioning.sql` which backfills `scope = '_legacy'`).

---

## TL;DR — what you have to change

If you embed `lunaris` in a Rust binary:

1. Every primitive constructor (`Episode::new`, `Chunk::new`, `Entity::new`,
   `Relation::new`, `Fact::new`, `Community::new`) now takes **`scope: Scope` as
   the first argument**.
2. Every `StoragePort` method that touches a partitioned resource now takes
   **`scope: &Scope` as the first argument after `&self`**. That's 8 methods:
   `atomic_write`, `vector_search`, `graph_traverse`, `scan_range`,
   `read_as_of`, `publish`, `subscribe`, `queue_depth`. `capabilities()` is
   unchanged.
3. The preferred way to ingest is now `engine.scoped(scope).ingest(builder)`,
   not `engine.ingest(episode)`. The new API constructs the `Episode` from an
   `EpisodeBuilder` and stamps the bound scope. Bare `Lunaris::ingest(Episode)`
   still works (it reads `episode.scope`) but is the discouraged path.
4. If you hit Lunaris over HTTP via `lunaris-server`, the JWT `tenant` claim
   is parsed into `Scope` at the auth middleware. Request bodies **must not**
   include a `tenant` or `scope` field — they are rejected with HTTP 422.

If your backend is Postgres, you also need:

- The new sqlx migration `20260510000005_scope_partitioning.sql` adds the
  `scope` column + RLS policies. **Run migrations on a clean shutdown.**
- Connect via a **non-superuser** role (`NOSUPERUSER NOBYPASSRLS`). Superusers
  bypass RLS and silently disable scope isolation. See §6 below.

If your backend is Moon:

- The migration is automatic — Moon keys gain a `lunaris:{scope}:` prefix on
  first write per scope. Old `lunaris:` keys are unreachable after upgrade and
  should be removed via the migration script. See §7 below.

## 1. Construct a `Scope`

```rust
use lunaris_core::Scope;

let scope = Scope::new("acme:agent-42")?;
// or, for tests:
let dev = Scope::dev();  // doc-hidden helper, do not use in production
```

Scope identifiers must match `^[A-Za-z0-9_\-:.]{1,128}$`. Invalid inputs
return `ScopeError::Invalid`.

## 2. Primitive constructors

```rust
// 0.1
let ep = Episode::new("notes.md", "Hello world", &clock);

// 0.2
let scope = Scope::new("acme:agent-42")?;
let ep = Episode::new(scope.clone(), "notes.md", "Hello world", &clock);
```

Same shape change for `Chunk::new`, `Entity::new`, `Relation::new`,
`Fact::new`, `Community::new`. The scope field is `pub scope: Scope` on each
struct.

## 3. Ingest path

The recommended ingest entry point is now `ScopedLunaris<'a>::ingest`:

```rust
// 0.1
let lsn = engine.ingest(episode).await?;

// 0.2 — preferred
let lsn = engine.scoped(scope.clone())
    .ingest(EpisodeBuilder::new("notes.md", "Hello world"))
    .await?;

// 0.2 — bare path still works (reads episode.scope)
let ep = Episode::new(scope, "notes.md", "Hello world", &clock);
let lsn = engine.ingest(ep).await?;
```

`EpisodeBuilder` is intentionally scope-less — only
`ScopedLunaris::ingest` can stamp a scope onto the underlying `Episode`. This
makes "ingest into agent A, retrieve from agent B" a compile error rather
than a silent leak.

## 4. Retrieval path

Bare `engine.recall()` still returns a `RetrievalBuilder` for backwards
compatibility. The wrapper exposes the same DSL with the bound scope:

```rust
// 0.1
let hits = engine.recall()
    .with_root(Vector::new("chunks", 30).top(5))
    .execute(Query::text("Alice"))
    .await?;

// 0.2 — preferred
let hits = engine.scoped(scope.clone())
    .recall()
    .with_root(Vector::new("chunks", 30).top(5))
    .execute(Query::text("Alice"))
    .await?;
```

> **Wave 1 known gap.** The retrieval DSL operators (`Vector`, `Graph`,
> hydration) currently use `Scope::dev()` internally as a placeholder when
> reading from storage. Wave 1F/Wave 2 will route the bound scope through
> `QueryContext`. Cross-scope isolation at the retrieval layer is therefore
> **not yet enforced** in the Wave 1 cut — track issue (TBD) for Wave 2.

## 5. Custom `StoragePort` implementations

If you wrote a custom backend implementing `StoragePort`, the trait shape
changed:

```rust
// 0.1
#[async_trait]
impl StoragePort for MyBackend {
    async fn atomic_write(&self, ops: &[WriteOp]) -> Result<Lsn, StorageError> { ... }
    async fn vector_search(&self, index: &str, query: &[f32], k: usize, ...) -> ... { ... }
    // ... 6 more methods, all without scope
}

// 0.2
#[async_trait]
impl StoragePort for MyBackend {
    async fn atomic_write(&self, scope: &Scope, ops: &[WriteOp]) -> Result<Lsn, StorageError> { ... }
    async fn vector_search(&self, scope: &Scope, index: &str, query: &[f32], k: usize, ...) -> ... { ... }
    // ... 6 more methods, scope: &Scope is now the first arg after &self
}
```

`WriteOp` variants did **not** gain a scope field — the trait method's `scope`
parameter is authoritative for the whole batch. A single `atomic_write` is by
definition one scope; cross-scope atomic writes are out of scope for v0.2.

## 6. Postgres deployment

Wave 1B added `scope TEXT NOT NULL` columns + RLS policies to every primitive
table. Two operational requirements:

### 6.1 Run the new migration

```bash
sqlx migrate run --source crates/lunaris-storage-postgres/migrations \
                 --database-url $LUNARIS_PG_URL
```

The migration backfills pre-existing rows with the reserved literal
`scope = '_legacy'`. After upgrade, those rows are queryable only under
`Scope::new("_legacy")`.

### 6.2 Use a non-superuser connection role

**Important:** Postgres superusers (`rolsuper=t`) and roles with
`BYPASSRLS` skip every RLS policy regardless of `FORCE ROW LEVEL SECURITY`.
Production deployments must connect via a dedicated role:

```sql
CREATE ROLE lunaris_app WITH LOGIN PASSWORD '…' NOSUPERUSER NOBYPASSRLS;
GRANT USAGE ON SCHEMA public TO lunaris_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO lunaris_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO lunaris_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO lunaris_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT USAGE ON SEQUENCES TO lunaris_app;
```

Connect with `postgres://lunaris_app@host/lunaris`. If you observe
cross-scope reads in your test environment, **check the role first** — the
RLS test in `crates/lunaris-storage-postgres/tests/scope_isolation.rs` is a
false-pass when run as a superuser.

## 7. Moon deployment

Wave 1C added per-scope keyspace prefix `lunaris:{scope}:` to every Moon key,
plus per-scope FT indices, GRAPH keys, and MQ topics. Operational notes:

- **First write per scope is slower** — Moon creates the FT index lazily on
  first `atomic_write` per scope. Subsequent writes hit the warm index.
- **Soft cap of ~512 scopes per Moon node.** `StorageCapabilities` now
  exposes `max_scopes_recommended = 512` reflecting Moon's FT index limit
  before recall p99 degrades. Beyond that, plan for workspace-per-scope (RFC
  TBD) or Moon node sharding.
- **Old `lunaris:` keys are unreachable** after upgrade — no key prefix
  rewrite happens automatically. The Wave 4 migration script handles the
  rewrite; for development, just drop and re-ingest.

## 8. HTTP API (`lunaris-server`)

The JWT `tenant` claim is now validated via `Scope::new()` at the auth
middleware. Tokens with malformed tenant claims return HTTP 401.

Request bodies for `POST /ingest`, `POST /recall`, `POST /forget` reject
unknown fields via `#[serde(deny_unknown_fields)]`. Specifically:

- `metadata.tenant` was previously silently honored as a tenant key. **Now
  rejected** with HTTP 422. The JWT `tenant` claim is the only source of
  truth for scope.
- A `scope` field at the top level of the request body is also rejected
  with HTTP 422.

If you were stamping tenant via request body in 0.1, switch to JWT-bound
scope in 0.2.

## 9. SDKs (`lunaris-py`, `lunaris-ts`)

SDK regen lands in **Wave 3 (subagent G)**. Until then, the v0.1 SDKs do not
compile against the v0.2 trait surface. Helios consumer migration is
similarly **Wave 3 (subagent H)**.

If you have a custom Python or TypeScript binding that calls into Lunaris,
plan to re-cut after v0.2 release.

## 10. Known operational constraints (v0.2.0)

These are documented contracts that v0.2.0 ships with; v0.2.1 / v0.3 will
remove or harden each one.

### 10.1 Scope strings MUST NOT end in primitive-kind suffixes

The KV key format is `lunaris:{scope}:{kind}:{ulid}`. The Wave 0 validation
regex `^[A-Za-z0-9_\-:.]{1,128}$` allows `:` in scope identifiers, so a scope
string `"a:episode"` produces the same `scope_prefix` byte sequence as
`Scope("a")`'s `episode_prefix`. On Moon, `SCAN MATCH <prefix>*` under the
colliding scope can enumerate the other scope's episodes.

**Operator contract for v0.2.0:** JWT issuers MUST NOT mint scope strings
ending in `:episode`, `:chunk`, `:entity`, `:relation`, `:fact`, or
`:community`. Postgres backends are unaffected — the `scope` column is
RLS-bound, not prefix-bound. v0.2.1 will tighten the regex to drop `:`
entirely (planned breaking change at the regex boundary; existing scopes
that contain `:` will need to be rewritten).

### 10.2 `Lunaris::forget` is a silent zero-match on real scopes

`Lunaris::forget` still routes through `Scope::dev()` internally for the
`atomic_write`, `read_as_of`, and `scan_range` calls — a same-scope forget
under any non-`_dev_` scope returns `rows_deleted=0, rows_written=0` with
no error. The cross-scope contract documented in
`docs/multi-agent.md` §"cross-scope forget" still holds (cross-scope is
always zero-match by design), but **same-scope forget is also broken in
v0.2.0**. Tracked for v0.2.1 (warn-on-non-dev-scope) and v0.3
(`ScopedLunaris::forget(target)` overload that routes the bound scope).

### 10.3 v0.2 release-gate review highlights

The full v0.2 release-gate code review is captured in
`tmp/v0.2-code-review.md`. Items closed at HEAD:

- **RC-1** — `Lunaris::ingest` (graph-on) now writes Fact KV rows under
  `lunaris_core::keyspace::fact_key(&scope, id)` (was unscoped).
- **RC-3** — Postgres RLS policies now declare both `USING` and
  `WITH CHECK` so INSERT/UPDATE row-side scope mismatches are rejected at
  the database boundary (migration `20260511000006_rls_with_check.sql`).
- **RC-4** — `Scope` deserialization now re-validates against
  `Scope::new` instead of trusting the wire bytes.
- **P-1** — `RecallRequest` and `ForgetRequestDto` both gained
  `#[serde(deny_unknown_fields)]`. All three HTTP body DTOs now reject the
  `scope` / `tenant` smuggling vector.

Items deferred to v0.2.1:

- **RC-2** — see §10.1 above. Tightening regex to drop `:`.
- **P-2** — `Lunaris::forget` warn-on-non-dev-scope. See §10.2 above.
- **P-3** — supervisor `register_scope` TOCTOU between fast-path check
  and idle-timeout deregistration. No reproducer; mitigated by operator
  re-calling `register_scope`.
- **P-5** — extend the scope-propagation regression matrix beyond
  `vector_search` to cover `graph_traverse`, `read_as_of`, `publish`,
  `subscribe`, and `scan_range`.

## 11. Known debt + Wave 2 follow-ups

The following items are tracked debt to close in Wave 2 before v0.2 ships:

- **`KeywordPort` lacks `&Scope`.** Per RFC §3.4 the original list missed
  the keyword search trait. BM25 keyword search is not scope-isolated at the
  trait level. RFC amendment + patch in Wave 2.
- **79 `Scope::dev()` migration crutches** in production paths
  (`forget.rs`, `recall.rs`, `verify/worker.rs`, hydrate, retrieve operators).
  Each is a documented stub with comment citing Wave 1D / Wave 3F follow-up.
- **Architectural smell** — `lunaris-ingest` imports `chunk_key` /
  `episode_key` from `lunaris-storage-moon::keyspace`. Storage-specific key
  formats are leaking into the engine layer. Wave 2 will move the keyspace
  helpers to `lunaris-core` so the dependency arrow points the right way.

## Appendix — Full public-API diff

Reproduce with:
```bash
cargo install cargo-public-api --locked
cargo public-api -p lunaris-core diff v0.1.2..HEAD
cargo public-api -p lunaris diff v0.1.2..HEAD
```

Summary across the workspace public surface:

| Crate            | Removed | Changed | Added (new public types)                                  |
|------------------|---------|---------|-----------------------------------------------------------|
| `lunaris-core`   | 0       | 17      | `Scope`, `ScopeError`, `scope` field on 6 primitives      |
| `lunaris`        | 0       | 0       | `EpisodeBuilder`, `ScopedLunaris<'a>`, `Lunaris::scoped`  |
| `lunaris-server` | 0       | 1       | `AuthClaims.scope` replaces `AuthClaims.tenant`           |

Zero items were removed from the public API. Every change is a parameter
addition or a new public type — no method renames, no behavior-preserving
refactors of existing call sites. This makes the migration mostly a
"add `scope` as the first argument" mechanical pass.
