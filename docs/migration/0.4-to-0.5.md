# Migrating 0.4 → 0.5

`v0.5.0` closes the **mem0-parity-hardening** P1 wave and relicenses the
project. There are **no breaking public API changes** — `cargo-semver-checks`
is green against the `v0.4.0` baseline for `lunaris-core` and `lunaris`. Most
consumers upgrade by bumping the version pin and rebuilding.

```bash
# Rust
cargo add lunaris-memory@0.5.0          # import as `lunaris`
# Python
pip install -U lunaris==0.5.0
# TypeScript
npm install @pilotspace/lunaris@0.5.0
```

## 1. License: Apache-2.0 only (was dual Apache-2.0 OR MIT)

Lunaris is now licensed under **Apache-2.0 alone**. The dual `Apache-2.0 OR
MIT` option is removed; `LICENSE-APACHE` / `LICENSE-MIT` are gone and the root
`LICENSE` now carries the full Apache-2.0 text.

**What you need to do:** nothing, unless your compliance process specifically
required the MIT option. Apache-2.0 is permissive (commercial use,
modification, distribution, private use) with an explicit patent grant. If you
pinned the SPDX expression `Apache-2.0 OR MIT` in your own allow-list, update it
to `Apache-2.0`. `deny.toml` is unchanged — Lunaris's *dependencies* remain
permissive (Apache-2.0 / MIT / BSD / ISC / Unicode).

## 2. New: framework SDK adapters (`lunaris_integrations`)

A new **pure-Python** package, installed separately from the native `lunaris`
core wheel, drops Lunaris into the common agent frameworks over one shared
`LunarisClient`:

| Framework | Class | Maps to |
|---|---|---|
| LangGraph | `LunarisStore(BaseStore)` | `aput`/`aget`/`asearch` → ingest/recall |
| CrewAI | `LunarisCrewAIStorage(BaseRAGStorage)` | `save`/`search`/`reset` → ingest/recall/forget |
| Letta | `LunarisArchivalConnector` | `insert`/`search` → ingest/recall (connector shim + recipe) |

Pick a transport: `HttpLunarisClient` (talks to a `lunaris-server`; the scope
stays JWT-bound server-side and is never sent on the wire), `SdkLunarisClient`
(wraps the in-process `lunaris-py` handle), or `StubLunarisClient` (for tests —
no backend/model/wheel required). `namespace → scope` is validated through the
RFC 0001 Scope alphabet (`[A-Za-z0-9_\-.]{1,128}`, `:` rejected). Adapters are
version-guarded and raise `UnsupportedFrameworkVersion` if your framework
version drifts outside the tested range. See `examples/letta-lunaris/` for the
Letta recipe.

## 3. Behavior change: structured ingest now converges memories

This is the one **behavioral** (not API) change to be aware of. Previously,
`ingest_structured` only ever *appended* facts. As of 0.5.0 it **converges**:

- **Dedup (synchronous).** Facts now carry a deterministic
  `FactId::from_triple(subject, predicate, object)`. Re-asserting an identical
  `(subject, predicate, object)` triple overwrites in place instead of creating
  a duplicate row.
- **Cross-episode contradiction (asynchronous).** A *different* object for the
  same `(subject, predicate)` with an **overlapping** validity window is
  detected at ingest, published as a needs-review item, and resolved by the
  existing async verifier (latest-assertion-wins), which closes the superseded
  fact's bi-temporal interval. A *disjoint* window appends as legitimate
  temporal succession (no false supersede).

Bi-temporal MVCC remains the source of truth — nothing is destroyed; superseded
facts are interval-closed and still visible to `as_of` time-travel queries. If
you previously deduplicated on the read side, you can drop that workaround.
There is no migration step for existing data; convergence applies to new
ingests, and the verifier reconciles contradictions as they are observed.

## 4. Known issue (unchanged from 0.4)

The CI `cargo_deny` advisory gate is red repo-wide on the pyo3 0.26.0
advisories (RUSTSEC-2026-0176 / -0177); resolving them needs a pyo3 lockstep
minor bump, tracked separately. This does not affect the published artifacts or
the runtime — it gates the supply-chain check only.
