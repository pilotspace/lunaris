# Moon MQ wire format: `body` field (mq-typed-client, contract v1)

**Audience:** operators running Lunaris on the Moon backend with the
consolidate/verify queues enabled. SQLite and Postgres backends are
unaffected.

## What changed

`lunaris-storage-moon`'s queue path now speaks the typed `moondb::MqClient`
wire shape. Stream entries written by `publish` carry a single **`body`**
field holding the payload bytes. The previous layout wrote two fields,
`partition <n>` and `payload <bytes>`.

`partition` was always write-only metadata — no Lunaris reader ever
consumed it from the wire (`QueueMsg.partition` echoes the subscriber's own
argument) — so it is now API-level only and absent from the stream entry.

## Operator action — drain before deploy

Messages already sitting in a Moon stream at upgrade time are in the legacy
layout. The new subscriber drains them **leniently**: a popped entry without
a `body` field is yielded with an EMPTY payload and ACKed, so queues never
wedge — but the legacy payload bytes are not recovered.

To avoid losing in-flight queue payloads:

1. Stop producers (pause ingest / scratchpad consolidation triggers).
2. Let consumers drain the `lunaris:{scope}:consolidate` /
   `lunaris:{scope}:verify` topics (they normally drain in seconds).
3. Deploy the new build, then resume.

If a queue was already empty at deploy time (the common case for
consolidate queues, which drain on a tight poll loop), no action is needed.

## External consumers

If any tooling outside Lunaris POPs Lunaris MQ topics directly with its own
parser, update it to read the `body` field instead of `payload`.

## Related finding

Moon v0.3.0's `MQ PUBLISH` works inside `TXN.BEGIN … TXN.COMMIT` with
correct atomicity (not visible before commit, visible after) — verified by
`crates/lunaris-storage-moon/tests/mq_typed_client.rs::mq_publish_txn_probe`.
In-transaction queue publishing is therefore available for future work
(e.g. enqueueing consolidation events inside the ingest `atomic_write`
transaction).
