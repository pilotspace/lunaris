# FT.NAVIGATE graph linkage: `_key` on entity nodes (ft-navigate-recall, contract v1)

**Audience:** operators running Lunaris on the Moon backend (v0.3.0+) who
want graph-expanded recall (`Navigate` DSL operator / `vector_navigate`
port method). SQLite and Postgres backends are unaffected — they report
`graph_navigate_native = false` and the `Navigate` operator silently
degrades to plain vector search.

## What changed

`lunaris-storage-moon`'s `WriteOp::GraphNode` writer now creates **new**
graph nodes via `GRAPH.ADDNODE` carrying a `_key` property — the entity's
FT doc key (`lunaris_{scope}_entities_idx:{hex(entity_id)}`). `GRAPH.ADDNODE`
is the only Moon v0.3.0 write path that registers the key→node mapping
`FT.NAVIGATE`'s graph expansion uses; Cypher `MERGE`/`CREATE`/`SET` never
do. All other node properties still flow through a Cypher `SET` (quoted
literals keep string typing — `GRAPH.ADDNODE`'s property parser would
silently coerce an all-digit hex id to a Float and break `WHERE n.id='…'`
matches).

Existing-node updates are unchanged (Cypher `SET` keyed by `WHERE n.id`),
and the whole flow still rides the single `atomic_write` transaction
(INGEST-04 intact; `GRAPH.ADDNODE` rolls back on `TXN ABORT`).

## Operator note — old nodes are not navigable

Graph nodes written **before** this version have no `_key` property, so
`FT.NAVIGATE` cannot expand through them: navigate over such a graph
returns KNN-only hits (`__hop_depth = 0`), which is exactly the
plain-vector-search result — recall quality never regresses, the graph
expansion just contributes nothing.

To make a pre-existing scope fully navigable, re-ingest it (the
existence-check + ADDNODE path only fires for nodes that don't exist yet,
so a re-ingest into a **fresh scope** is the clean route; in-place
re-ingest updates props but cannot retrofit `_key` onto a node Moon has
already created via MERGE).

A future Moon release may register `_key` from Cypher writes, which would
allow an in-place backfill — tracked as an open delta in the ADD task.

## Interaction with `GRAPH.QUERY` reads

`_key` is an ordinary string property: Cypher can read and match it
(`WHERE n._key = '…'`). It is reserved for Lunaris' own linkage — do not
overwrite it from agent-supplied structured ingest.
