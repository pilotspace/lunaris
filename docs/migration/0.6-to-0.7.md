# Migrating 0.6 → 0.7: Moon-only storage

**Status: current.** Both slices have landed. Slice A shipped the
`lunaris-migrate` tool on the 0.6.x line; slice B deleted
`lunaris-storage-postgres`, `lunaris-storage-embedded`, and `lunaris-migrate`
itself from the workspace. This document is the operator exit ramp, and §7
records exactly what changed in code.

**Read §6 first if you have data to move.** `lunaris-migrate` cannot be built
from `main` any more — its source backends are gone. Run it from the **v0.6.2
release binary, before you upgrade.**

## TL;DR

| 0.6 | 0.7 |
|---|---|
| `moon://`, `postgres://`, `sqlite:///path`, `memory://` | `moon://` only |
| `lunaris-storage-postgres`, `lunaris-storage-embedded` crates | deleted |
| bi-temporal `read_as_of` served by Postgres/SQLite version chains | Moon has no KV version chain — historical reads are refused, not faked |
| — | `lunaris-migrate` (0.6.x only) moves your data before you upgrade |

If you already run `moon://`, there is nothing to migrate. Everyone else runs
`lunaris-migrate` **before** upgrading the server.

**Rollback:** the deployment-side upgrade/rollback order of operations for
0.6.2 ↔ 0.7.0 — both directions, including why the retired 0.6.2 store's
retention window *is* your rollback budget — lives in
[`docs/RELEASE.md` §7](../RELEASE.md#7-deployment-upgrade--rollback--062--070)
(rehearsal is a GA-4 gate, currently PENDING).

## 1. The lossy contract

`lunaris-migrate` prints this before it does anything, and refuses to write
without `--acknowledge-lossy`. It is not boilerplate — each clause corresponds
to a mechanism:

| What | Why |
|---|---|
| **Sys-time history collapses to migration time** | `WriteOp` carries no bi-temporal or LSN input (`KvPut { key, value }` is the whole write surface) and no backend has a backdating write. The destination stamps every row with its own HLC tick at migration time. The record's own `bt` payload is preserved verbatim *inside the value*; it is the storage-level sys interval that is re-stamped. |
| **Superseded versions do not travel** | The embedded backend keys `lunaris_kv` on `(key, sys_from)` and closes `sys_to` on overwrite; Postgres does the same. Moon KV is a single-field hash with no version chain, which is why `MoonStorage::supports_historical_kv_reads()` is `false`. Only the row current at migration time can be represented. |
| **Closed intervals are skipped, and counted** | A row with `bt.valid.1` set was retracted or superseded in the world; a row with `bt.sys.1` set was logically deleted. Copying either into a store that cannot express "was true until T" would present retracted state as current. |
| **Derived indexes are not carried** | See §4. |
| **Superseded sys-version counts are `not enumerable`** | A `StoragePort` reader sees one live row per key, and the destination refuses historical `as_of`. The report says so instead of printing a `0` that would read as "there were none". |

### Skip-count semantics

The per-scope report distinguishes four classes. Only the first three are
numbers; the fourth is deliberately not:

- `skipped: closed valid interval` — record retracted/superseded in the world.
- `skipped: closed sys interval` — record logically deleted.
- `skipped: foreign/malformed key` — a key under `lunaris:{scope}:` that does
  not parse as `lunaris:{scope}:{kind}:{id}`, or that carries another scope's
  segment. Left behind on purpose: a stray key is an operator signal, not cargo.
- `skipped: superseded sys versions` — **`not enumerable`**, per the table above.

## 2. Procedure

```bash
# 0. Bring up the destination Moon and confirm the version handshake passes.
redis-cli -h <moon-host> -p <moon-port> INFO server | grep moon_version

# 1. Report. This is the default; it writes nothing.
lunaris-migrate --from sqlite:///var/lib/lunaris/store.db \
                --to   moon://<moon-host>:<moon-port> \
                --all-scopes

# 2. Read the contract and the counts. Then commit.
lunaris-migrate --from sqlite:///var/lib/lunaris/store.db \
                --to   moon://<moon-host>:<moon-port> \
                --all-scopes \
                --commit --acknowledge-lossy \
                --reembed-manifest /tmp/lunaris-reembed.jsonl

# 3. Regenerate vectors from the manifest (see §4), then cut traffic over.
```

### `--vector-dim` — read this if your embedder is not 768-d

The migration writes no vectors, but **opening a Moon handle creates the
`chunks` / `entities` / `facts` / `communities` FT indices** when they are
absent, and `FT.CREATE`'s `DIM` is **sticky** — Moon does not resize. So the
width this tool connects at becomes the destination's width for every future
ingest. It defaults to `768` (granite-r2, the production embedder). If you run
a different embedder, say so:

```bash
lunaris-migrate --from ... --to ... --all-scopes --vector-dim 1536
```

Getting it wrong is recoverable only by `FT.DROPINDEX chunks entities facts
communities` plus a full re-ingest. If the destination Moon already holds
indices at another width, `connect` refuses the handle rather than writing into
a mismatched store.

Postgres sources: `--all-scopes` does **not** work. `list_scopes` returns
`NotSupported` on Postgres by design — its RLS boundary forbids a cross-scope
`SELECT DISTINCT scope`, and weakening that boundary for a migration would be
the wrong trade. Pass explicit, repeatable `--scope` arguments:

```bash
lunaris-migrate --from postgres://lunaris@db/lunaris \
                --to   moon://<host>:<port> \
                --scope acme.agent-1 --scope acme.agent-2 \
                --commit --acknowledge-lossy
```

The Postgres source opens with `connect_no_migrate`: a migration source is
read-only, and running DDL against the store you are leaving is not this tool's
business.

### Re-run semantics

Keys are deterministic (`lunaris:{scope}:{kind}:{ulid}`) and every write is an
idempotent `KvPut`. Re-running overwrites in place and cannot duplicate. Two
uses follow from that:

- **Resume**: a run interrupted mid-way is fixed by re-running it. Atomicity is
  per `--batch-size` batch, so at most one batch is ever partially applied, and
  re-writing it is a no-op.
- **Incremental top-up**: run once ahead of the maintenance window, then again
  during it to carry the delta.

### Verification

Every committing run ends with a verification pass (disable with
`--no-verify`). It re-reads **both sides through `StoragePort`** — proving what
an application will see, not what the writer believed it wrote — and reports:

- per-kind counts on the source (eligible rows) and the destination,
- presence of every eligible source key on the destination (`missing`),
- a byte-for-byte comparison of `--sample` keys spread by stride across the key
  range, so a truncated write is as visible as a corrupt one (`mismatched`),
- `dest_only`: destination keys with no eligible source counterpart.
  Informational — that is the re-run and pre-existing-data case.

`missing > 0` or `mismatched > 0` fails the pass and the process exits `2`.

## 3. What does NOT migrate — queues and idempotency

- **Queue state** (`publish`/`subscribe`, pgmq or Moon MQ) is not copied. Drain
  your consumers before migrating.
- **Dedupe sidecar rows** are copied when they live under the scope prefix as KV
  (`lunaris:{scope}:dedupe:{hash}`). The Postgres/SQLite `lunaris_dedupe` TABLE
  is *not* — it is not reachable through `StoragePort`. Expect at most a repeat
  ingest of anything you replay across the cutover.

## 4. Embeddings, BM25, and the graph — the honest story

**Recall on the destination returns nothing until you re-embed.** Three facts
force this, and all three were checked rather than assumed:

1. **KV payloads carry no vectors.** `Chunk`, `Entity`, `Fact` and `Community`
   mark `embedding` `#[serde(default, skip_serializing)]` (since `6093a9f`), so
   the bytes `scan_range` returns cannot contain one.
2. **`StoragePort` has no vector enumeration.** `vector_search` is a k-bounded
   ANN probe against a named index, not a dump. The source's vectors are
   therefore unreachable through the contract this tool is permitted to use.
3. **On Moon, FT documents are separate keys.** `VectorUpsert` writes
   `lunaris_{scope}_{kind}_idx:{id_hex}`; `KvPut` writes
   `lunaris:{scope}:{kind}:{ulid}`. Copying KV creates no FT document — and
   Moon's BM25 path reads the same FT index as the vector path, so **keyword
   search is dead too**, not just semantic search. The graph projection
   (`GraphNode` / `GraphEdge`) is likewise absent.

The rejected alternative was re-embedding inside the migration tool. That means
linking the llama.cpp runtime into a migration binary and silently re-deriving a
model-version-dependent artifact during a data move — a worse failure mode than
a declared gap, because a wrong-model embedding is invisible until recall
quality degrades.

So the tool carries the durable record, declares the derived state, and hands
you the backlog: `--reembed-manifest <path>` writes one JSONL line per key that
needs a vector.

```json
{"scope":"acme.agent-1","kind":"fact","key":"lunaris:acme.agent-1:fact:01H…"}
```

**There is no `lunaris reindex` command, and 0.7.0 does not add one.** The
manifest is an input to a re-ingest of the affected primitives: read each
`key`, and re-ingest the episode it belongs to through the normal ingest path,
which derives chunks, embeddings, FT documents and graph projection together.

That is a deliberate non-decision rather than a deferral. A `reindex` command
would have to re-derive vectors from KV payloads that (per fact 1 above)
deliberately do not carry them, using whatever embedder the reindexing process
happens to resolve — reintroducing exactly the model-version hazard the
rejected in-tool re-embed had. Re-ingest is slower and completely honest about
which model produced the vectors, because it is the same path production uses.

## 5. Bi-temporal reads after the move

Moon cannot answer a historical `read_as_of` — it refuses rather than returning
present-time data (0.6.2 hardening). If you depend on historical snapshots,
that dependency does not survive 0.7.0 on Moon. Keep the old store readable
(offline, out of the serving path) for as long as you need to answer historical
questions; `lunaris-migrate` never mutates the source.

## 6. How the migration tool survives 0.7.0

**It does not, and that is the design.** `lunaris-migrate` is pinned to the
0.6.x line — the last one where all three backends compile in a single
workspace — and is deleted alongside `lunaris-storage-postgres` and
`lunaris-storage-embedded` in 0.7.0. Run migration from a **0.6.x build**, then
upgrade.

Options considered:

| Option | Verdict |
|---|---|
| Pin published crates.io versions of the storage crates as the tool's deps | **Rejected.** Two `lunaris-core` versions end up in one binary, and `StoragePort` from 0.6 and 0.7 are different traits — the tool would need a hand-written bridge nobody exercises. Moot anyway: `lunaris-storage-moon` depends on `moondb` by *path* (`vendor/moon/sdk/rust`), so it is not on crates.io to pin. |
| Keep the source backends in-workspace as migrate-only deps | **Rejected.** Slice B's deletion becomes cosmetic: the code still has to compile — and therefore be maintained — against every 0.7.x change. |
| **Run migration on the 0.6.x release binary** | **Chosen.** Zero ongoing maintenance. The tool is frozen at the last version where both sides provably exist, which is also the only version where its behaviour can be tested end to end. |

Consequence for distribution: `cargo install lunaris-migrate` is **not** a
supported path (`publish = false`, and the `moondb` path dependency makes the
registry route impossible regardless). Build it from the 0.6.x tag:

```bash
git checkout v0.6.2 && git submodule update --init vendor/moon
cargo build --release -p lunaris-migrate
./target/release/lunaris-migrate --help
```

Building from the tag is the supported path and always works. A prebuilt
`lunaris-migrate` binary attached to the v0.6.2 GitHub release is a
**release-ops action, not a code change** — no workflow in this repo produces
one (`crates/lunaris-migrate` was `publish = false`, and mcp-prebuild.yml only
covers `lunaris-mcp`). Until an operator uploads one, treat the `git checkout
v0.6.2` recipe above as the only distribution channel and do not point users at
a download that may not exist.

## 7. Code changes in 0.7.0

Everything below is a compile-time or startup-time break. None of it fails
silently.

### Storage URLs

`lunaris::open` / `Lunaris::open` accept `moon://host:port` and nothing else.
`postgres://`, `postgresql://`, `sqlite:///path` and `memory://` return
`StorageError::UnsupportedScheme` carrying the migration instructions — the
tool, the release it ships in, and a pointer back to this document. A scheme
Lunaris never served gets the plain error, without the migration prose.

### Removed public API

| Removed | Replacement |
|---|---|
| `lunaris::PostgresStorage` | none — open a `moon://` URL |
| `lunaris::BootstrapReport`, `lunaris::bootstrap_app_role` | none — Moon has no role bootstrap |
| `lunaris_storage_postgres::*`, `lunaris_storage_embedded::*` | the crates are deleted |
| `lunaris-server migrate` | none — Moon needs no schema migration |
| `lunaris-server bootstrap-db` | none — Moon needs no app role |
| the `pg-it` cargo feature | removed from every crate that declared it |

Both retired `lunaris-server` subcommands still parse: the binary prints what
the subcommand used to do, why it is gone, and where to go instead, then exits
`2`.

### Storage is now required, everywhere

No binary picks a store on your behalf. Each of these had a default that
resolved to a backend that no longer exists:

| Binary | Old default | 0.7.0 |
|---|---|---|
| `lunaris-mcp` | `sqlite:///<HOME>/.lunaris/<scope>.db` | `--storage` / `LUNARIS_MCP_STORAGE` required; startup refusal names the fix |
| `lunaris-hook` | same file, after `LUNARIS_STORE_URL` and contextd discovery | those two remain; otherwise a named error |
| `lunaris-bench` ER-F1 | `memory://` | `MOON_URL` (or `LUNARIS_URL`) required |

No replacement default was added, including `moon://127.0.0.1:6380`. A binary
that guesses can guess a store that already belongs to something else, and a
mis-routed agent memory is far harder to notice than a process that will not
start.

### Tests and the harness

`LUNARIS_TEST_BACKEND=memory` is removed. It selected the embedded backend, so
it is now a named hard error rather than a silent upgrade to Moon. Every
`lunaris-test-harness` fixture runs against a disposable child-process Moon;
when no `moon` binary resolves the harness PANICS with a message naming
`MOON_TEST_BINARY` and the `vendor/moon` build command. Unset, blank, `auto`
and `moon` are accepted and equivalent.

That makes a `moon` binary a build-time prerequisite for `cargo test
--workspace`:

```bash
cargo build --release --manifest-path vendor/moon/Cargo.toml --bin moon
cargo test --workspace --exclude lunaris-py --exclude lunaris-ts
```

CI does exactly this. The harness finds `vendor/moon/target/release/moon` on
its own search path, so `MOON_TEST_BINARY` is only needed to point somewhere
else.

### Bi-temporal reads

Unchanged from 0.6.2, and now the only behaviour available: see §5.
