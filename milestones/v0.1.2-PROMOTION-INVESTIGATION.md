# Zero-Promotion Investigation: EVAL-05 promotion_rate = 0.0

**Investigated:** 2026-04-25T17:58:00Z
**Phase:** 18 (audit debt closure)
**Covers:** Phase 18 SC2 (zero-promotion root cause analysis)

## Background

Plan 16-04 calibrated the EVAL-05 `promotion_rate` SLO across 6 runs (3 x Moon + 3 x Postgres). All 6 runs observed `promotion_rate = 0.0000`. The operator chose "widen-band" disposition, setting the enforced SLO band to `[0.00, 0.01]`. Phase 16 VERIFICATION flagged this as "structurally unverified" -- the band trivially accepts zero-promotion output including a potentially broken pipeline.

Three hypotheses were identified:
- **H1:** The 16-01 default flip does not propagate through the eval_05 code path
- **H2:** ACT-R promotes zero facts under default params for this trace shape
- **H3:** The debounce window exceeds the drain window

This document performs a static code-trace analysis of each hypothesis.

## Hypothesis Analysis

### H1: Default flip does not propagate through eval_05 code path

The eval_05 binary at line 270 calls `Lunaris::open(url)` which goes through the standard `handle.rs:119` path. At `handle.rs:139`, `default_consolidator()` delegates to `ConsolidatorPipelineHandle::backend_from_env()` at `consolidator_pipeline.rs:339`. With `LUNARIS_CONSOLIDATOR_BACKEND` unset, this resolves to `ActRConsolidator::default()` (line 343-345). The consolidator is installed into the pipeline handle at `handle.rs:146`.

This calls `consolidator_pipeline.rs:206` which sets `scope_prefix = Some("helios:fs/")`, flips `enabled = true`, and calls `spawn_worker_if_idle()` at line 250. Since storage was already bound at `handle.rs:162`, the worker spawns successfully via `consolidator_pipeline.rs:141-158`.

**Verdict:** RULED OUT -- The 16-01 default flip correctly propagates through the eval_05 code path. `ActRConsolidator::default()` is the resolved backend. The consolidator worker is spawned with scope `"helios:fs/"` and bound to live storage. The full pipeline is wired.

### H2: ACT-R promotes zero facts under default params for this trace shape

**Trace fixture analysis:**

The EVAL-05 trace is generated by `eval_05_trace.rs:76-111` (`Trace::new`). It produces 10,000 ops from a 500-path pool (`helios:fs/chat-turn-NNNN.md`). The op mix is:
- Read: 40% (~4,000 ops)
- Write: 30% (~3,000 ops)
- Edit: 15% (~1,500 ops)
- Grep: 15% (~1,500 ops)

Each write/edit flows through `HeliosScratchpad::write` -> `WorkingMemory::write` -> `Lunaris::ingest(episode)`.

**Critical finding: Every ingest creates a new episode_id.**

At `primitives.rs:27-36`, `Episode::new()` calls `Ulid::new()` on every invocation. This means every write to the same path (e.g., `helios:fs/chat-turn-0042.md`) produces a **distinct episode_id**. The consolidator groups events by `episode_id` (worker.rs:201, act_r.rs:267-269), so each episode receives exactly 1 `ConsolidateEvent`.

Additionally, reads and greps do NOT trigger `Lunaris::ingest`, so they do not produce consolidation events. Only writes (30%) and edits (15%) produce events -- approximately 4,500 total events across 4,500 distinct episode_ids.

**Activation math:**

With `promote_threshold = +1.0` (act_r.rs:102-103, ConsolidatorConfig default) and `decay = 0.5`:

For a single reference at elapsed time `t` seconds (floored at 1):
```
activation = ln(t^(-0.5)) = -0.5 * ln(t)
```

- At elapsed = 1s: `activation = ln(1^(-0.5)) = ln(1) = 0.0` -- NOT promoted (0.0 < 1.0)
- At elapsed = 2s: `activation = -0.5 * ln(2) = -0.347` -- NOT promoted
- At elapsed = 10s: `activation = -0.5 * ln(10) = -1.151` -- NOT promoted (archived at < -0.5)
- At elapsed = 60s: `activation = -0.5 * ln(60) = -2.047` -- NOT promoted (deep archive)

For promotion to occur (`activation > promote_threshold = +1.0`), we need `ln(sum) > 1.0`, i.e., `sum > e = 2.718`. With all references at elapsed = 1s (maximum favorable case), `sum = N * 1^(-0.5) = N`, so we need `N >= 3` references to the same episode_id (`ln(3) = 1.099 > 1.0`).

Since each EVAL-05 episode_id receives exactly 1 event (every write creates a new Ulid), the activation for every episode is at most `0.0` (when scored immediately) and decreases monotonically as time passes. No episode ever crosses the `promote_threshold = +1.0`.

**Corroborating evidence:** The `consolidator_scope_isolation.rs` test (Phase 16-02) proves ActR CAN promote when given sufficient reinforcement. That test uses **16 references per episode** (all at elapsed ~1s), producing `activation = ln(16) = 2.77 > 1.0`. It observes 20/20 promotions. The difference is that the isolation test reuses the same `episode_id` across multiple events; EVAL-05 does not.

**Verdict:** CONFIRMED -- ACT-R correctly produces zero promotions for the EVAL-05 trace shape. Each write creates a unique episode_id via `Ulid::new()`, so every episode receives exactly 1 `ConsolidateEvent`. A single reference produces `activation <= 0.0`, which never crosses `promote_threshold = +1.0`. This is mathematically correct Anderson 1996 base-level activation behavior for unreinforced episodes.

### H3: Debounce window exceeds drain window

**Timing analysis:**

- `DEFAULT_DEBOUNCE_MS = 60,000` (worker.rs:72) -- worker flushes buffer every 60 seconds
- `DEFAULT_DRAIN_SECS = 90` (eval_05_helios_10k.rs:89) -- eval_05 waits 90 seconds after replay

Timeline:
1. Worker spawns at `enable_for_scope` call (eval_05_helios_10k.rs:277)
2. Warm-up writes seed 500 paths (lines 286-289) -- these publish ~500 consolidation events
3. Trace replay runs 10,000 ops including ~4,500 writes/edits (lines 300-329)
4. 90-second drain window starts (line 338)
5. Worker's debounce timer fires at t=60s after spawn, flushing the buffer
6. During the 90s drain, at least one debounce flush occurs

The drain window (90s) exceeds the debounce window (60s) by 30 seconds. The worker's `tokio::select!` loop (worker.rs:130-166) processes the debounce timer at line 161 (`tokio::time::sleep_until(next_flush)`), which fires every 60s. So at least one flush cycle completes during the 90s drain.

However, even if timing were inverted, H2 is the binding constraint: the flush produces an `ActRConsolidator::consolidate()` call that correctly scores all single-reference episodes at `activation <= 0.0`, below the `promote_threshold = +1.0`. The timing is sufficient but irrelevant because the activation math forbids promotion regardless.

**Verdict:** RULED OUT -- The drain window (90s) exceeds the debounce window (60s). At least one flush cycle completes during drain. The timing is sufficient for the consolidator to process all buffered events. However, H2 is the dominant factor -- even with infinite drain time, no promotions would occur.

## Secondary Finding: Measurement Harness Blind Spot

Independent of H2, a secondary finding emerged from the code trace: the EVAL-05 promotion measurement is structurally unable to detect promotions even if they occurred.

**Evidence:**

1. `eval_05_helios_10k.rs:386-399` measures promotions via `count_facts(&mem)`, which calls `storage.scan_range(b"fact:", None)` to count `fact:*` keys.

2. The consolidator worker (worker.rs:283) calls `publish_per_event_audits(storage, &report)` after consolidation, which publishes `AuditEvent::ConsolidatorPromotion` envelopes to `__lunaris_audit__` (worker.rs:296-305). **The worker does NOT write `fact:*` keys to storage.**

3. `ActRConsolidator::consolidate` (act_r.rs:247-288) returns a `ConsolidationReport` with `PromotionEvent` entries in memory. The `synthesize_fact_id_from_episode` function (act_r.rs:137-146) generates a `FactId` from a blake3 hash, but this is used only in the audit envelope -- no storage write occurs.

4. By contrast, `consolidator_scope_isolation.rs` counts promotions by intercepting audit events published to `__lunaris_audit__` via a custom in-memory broker (line 222, line 370). This is why it correctly observes 20/20 promotions with 16 refs/episode.

**Implication:** `count_facts` in EVAL-05 would return 0 delta even if the consolidator DID promote episodes, because the worker publishes audit events but does not write `fact:*` keys. The EVAL-05 binary's `#[allow(unused_imports)] use lunaris_core::audit::{AUDIT_TOPIC, AuditEvent}` at line 64 suggests the harness author anticipated eventual migration to audit-based measurement.

## Root Cause

**Primary root cause: H2 (trace shape).** Each EVAL-05 write creates a unique `episode_id` via `Ulid::new()` at `primitives.rs:29`. The ACT-R consolidator groups by `episode_id` (act_r.rs:267-269), so every episode receives exactly 1 `ConsolidateEvent`. A single reference produces `activation = ln(1^(-0.5)) = 0.0` at best, which never crosses `promote_threshold = +1.0`. Zero promotions is the mathematically correct Anderson 1996 output for unreinforced episodes.

**Secondary finding: measurement blind spot.** Even if promotions occurred, EVAL-05's `count_facts(&mem)` would not detect them because the consolidator worker publishes audit events to `__lunaris_audit__` but does not write `fact:*` keys to storage. The scope-isolation test (which uses audit-event interception) is the valid promotion proof; `count_facts` is not.

## Disposition

Zero-promotion is **ACCEPTABLE** v0.1.2 behavior. No code change required for this milestone.

**Justification:**

1. **Pipeline is correctly wired (H1 ruled out).** `Lunaris::open()` -> `backend_from_env()` -> `ActRConsolidator::default()` propagates through the eval_05 code path. The worker spawns, binds to storage, and processes events through the full debounce -> consolidate -> audit pipeline.

2. **ACT-R correctly classifies unreinforced episodes as not worthy of promotion (H2 confirmed).** The Anderson 1996 activation formula produces `activation <= 0.0` for single-reference episodes. With `promote_threshold = +1.0`, zero promotions is the mathematically correct output. The EVAL-05 trace shape (unique `episode_id` per write) never produces the >= 3 reinforcements needed to cross the threshold.

3. **The scope-isolation test proves ActR promotes when given sufficient reinforcement.** `consolidator_scope_isolation.rs` uses 16 refs/episode and observes 20/20 promotions (via audit-event interception). The consolidator works; the EVAL-05 trace simply does not exercise the promotion path.

4. **The SLO band `[0.00, 0.01]` correctly reflects empirical reality.** The calibrated band matches the expected mathematical output for this trace shape.

5. **Timing is sufficient (H3 ruled out).** The 90s drain exceeds the 60s debounce; at least one flush completes.

**Recommendations for future milestones:**

- Multi-reinforcement traces (e.g., LoCoMo multi-session replay, or a synthetic trace that revisits the same `episode_id` across turns) would exercise the promotion path and produce measurable `promotion_rate > 0`.
- Migrate EVAL-05 promotion measurement from `count_facts` (scan `fact:*` keys) to audit-event subscription via `AUDIT_TOPIC` + `AuditEvent::ConsolidatorPromotion` -- the imports are already present at `eval_05_helios_10k.rs:64`.
