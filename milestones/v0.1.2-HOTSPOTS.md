## Top-3 Rust-Side Hotspots

### Analytical Pre-Audit (Code-Review-Based, Not Profiler-Verified)

The following hotspot candidates are identified from static analysis of the
EVAL-05 hot path (`HeliosScratchpad::read/grep` -> `Lunaris::recall` ->
`FuseRrfRetriever::retrieve` -> `fuse_via_moon_native` or `client_side_rrf` ->
`hydrate`). These are **candidate functions** -- actual self-time percentages
require flamegraph confirmation.

### Moon Backend (Analytical)

| Rank | Function / Call Site | Module | Analysis |
|------|---------------------|--------|----------|
| 1 | `storage.read_as_of()` (serial per-chunk KV fetch in hydrate loop) | `lunaris-retrieve/src/hydrate.rs:66` | Each recall issues N serial `read_as_of` calls (one per RawHit). On Moon this is N Redis RTTs over loopback. With 30 hits per recall across 5571 samples, this dominates wall-clock time. Note: parallel hydrate was attempted and reverted in v0.1.1 (stream scheduling overhead exceeded sub-ms RTT savings on loopback). |
| 2 | `serde_json::from_slice::<Chunk>` / `serde_json::from_slice::<Episode>` | `lunaris-retrieve/src/hydrate.rs:68,94` | Every hydrated hit deserializes a full `Chunk` struct from JSON. With bi-temporal fields, heading_path vectors, and text content, this is non-trivial serde work per hit. |
| 3 | `typed.text().hybrid_search()` (Moon SDK network call) | `lunaris-retrieve/src/fusion.rs:145` | The Moon-native hybrid_search is a single round-trip, but the server-side FT.SEARCH + RRF scoring is the primary latency contributor. This is outside Rust client control -- it measures Moon server performance. |

### Postgres Backend (Analytical)

| Rank | Function / Call Site | Module | Analysis |
|------|---------------------|--------|----------|
| 1 | `storage.read_as_of()` (serial per-chunk SQL query in hydrate loop) | `lunaris-retrieve/src/hydrate.rs:66` | Same serial hydration pattern as Moon. On Postgres this is N individual `SELECT ... WHERE key = $1 AND sys_from <= $2` queries. Connection pooling amortizes handshake but each query is a full parse/plan/execute cycle. |
| 2 | `serde_json::from_slice::<Chunk>` / `serde_json::from_slice::<Episode>` | `lunaris-retrieve/src/hydrate.rs:68,94` | Identical to Moon -- JSON deserialization overhead is backend-agnostic. |
| 3 | SQL query planning + pgvector distance computation | `lunaris-storage-postgres` (via sqlx) | Postgres vector_search involves `ORDER BY embedding <=> $1 LIMIT $2` which triggers an IVFFlat or HNSW index scan. The distance computation is in-database, not in Rust, but sqlx result parsing (`Row::get`) and type conversion show up on the Rust side. |

### HashMap Usage Analysis (Static)

The following `std::collections::HashMap` call sites exist on the hot path:

| Location | Type | Hot-Path Role | Estimated Impact |
|----------|------|---------------|------------------|
| `fuse.rs:114` | `HashMap<SourceOp, Vec<RawHit>>` | Bucketing hits by source_op in client_side_rrf | Low -- only reached on client-side fallback (not Moon-native path). Typically 2-3 buckets, <100 entries. |
| `fuse.rs:121` | `HashMap<Vec<u8>, f32>` | Accumulating RRF scores per hit ID | Low -- same fallback path. Key is 16-byte ULID Vec, typically <60 entries per recall. |
| `fuse.rs:122` | `HashMap<Vec<u8>, RawHit>` | Keeping best-scoring sample per hit ID | Low -- same as above. |
| `hydrate.rs:90` | `HashMap<Ulid, String>` | Episode source lookup cache (batch dedup) | Low -- typically <10 unique episodes per recall batch. |
| `hydrate.rs:147` | `HashMap<Vec<u8>, String>` | Partial hydrate text cache for reranker | Low -- bounded by k (typically 30). |
| `combinators.rs:100` | `HashMap<Vec<u8>, RawHit>` | Dedup in AndRetriever merge | Low -- bounded by 2k (typically 60). |

**Key observation:** On the Moon-native path (the default for EVAL-05), the
`client_side_rrf` HashMap operations in `fuse.rs` are **completely bypassed**
-- `FuseRrfRetriever::retrieve` short-circuits to `fuse_via_moon_native` which
returns hits directly. The only HashMap on the Moon-native hot path is the
episode source dedup in `hydrate.rs:90` (typically <10 entries).

## Hash-Map Analysis

No hash-map operation appears as a plausible top-3 hotspot on either backend
based on static analysis:

1. **Moon-native path bypasses client_side_rrf entirely.** The `FuseRrfRetriever`
   detects `VectorKeywordSameIndex` + `native_rrf=true` + `moon_storage.is_some()`
   and dispatches to `fuse_via_moon_native` (fusion.rs:88). The three HashMap
   instances in `client_side_rrf` (fuse.rs:114-122) are never allocated.

2. **Remaining HashMap usage is small-N.** The hydrate episode dedup
   (`HashMap<Ulid, String>` at hydrate.rs:90) typically holds <10 entries per
   recall call. At this scale, SipHash vs FxHash vs FoldhHash is
   indistinguishable -- the hash computation is <100ns total, dwarfed by the
   serial `read_as_of` network roundtrips (~0.5ms each on loopback).

3. **EVAL-05 evidence supports this conclusion.** Plan 15-04 showed Moon p50
   4.66-5.52ms on clean runs vs Postgres p50 5.67-7.45ms. The parity (ratio
   0.63-0.97x) indicates the bottleneck is I/O-bound (network RTTs to Moon/Postgres),
   not CPU-bound (hash computation). A hash-map swap would not move the p50 needle.

The audit is closed with the analytical evidence above. No speculative hash-map
swaps are applied. A cross-cutting cache-layout / SwissTable audit is deferred
to v0.2.x per ROADMAP.

## Verdict

- **Hash-map swap warranted: No**
- **Rationale:** No hash-map operation appears in the top-3 hotspot candidates
  on either backend. The Moon-native `hybrid_search` path bypasses all
  client-side HashMap usage. Remaining HashMap instances operate on <10-60
  entries where SipHash overhead is negligible compared to network I/O.
- **EVAL-05 evidence:** Moon p50 at parity with Postgres on clean runs
  (0.63-0.97x ratio per `milestones/v0.1.2-MOON-HYBRID-RESULTS.json`).
  The performance delta is I/O-bound, not CPU-bound.
- **Flamegraph confirmation:** Pending operator execution of `cargo flamegraph`
  commands documented above. If the flamegraph reveals an unexpected hash-map
  hotspot, reopen this audit with the SVG evidence.
- **Deferred:** Cross-cutting SwissTable / cache-layout audit to v0.2.x per ROADMAP.

## Appendix: Hot-Path Call Graph

```
HeliosScratchpad::read/grep
  -> Lunaris::recall(query)
    -> RetrievalBuilder::execute()
      -> FuseRrfRetriever::retrieve(ctx)
        -> [Moon-native path] fuse_via_moon_native(ctx, hint, k)
          -> ctx.embed_once()                          # OnceCell cached embedding
          -> typed.text().hybrid_search(...)            # Single Moon RTT
          -> decode_moon_vector_key() per hit           # O(k) hex::decode
          -> serde_json::from_str(__metadata) per hit   # O(k) JSON parse
        -> [OR client-side path] client_side_rrf(raw, k)
          -> HashMap bucketing by SourceOp              # 2-3 buckets
          -> HashMap RRF accumulation per hit ID        # <60 entries
      -> hydrate(storage, raw_hits, as_of)
        -> chunk_lookup_key() per hit                   # O(k) Ulid::from_bytes
        -> storage.read_as_of(key, snapshot) per hit    # O(k) serial network RTTs
        -> serde_json::from_slice::<Chunk>() per hit    # O(k) JSON deserialize
        -> episode_lookup_key() per unique episode      # O(n_unique) << k
        -> storage.read_as_of(ep_key, snapshot)         # O(n_unique) serial RTTs
```
